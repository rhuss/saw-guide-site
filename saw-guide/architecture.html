Architecture

Figure 1. SAW architecture: shared services, per-user namespaces, and what runs inside each VM.

SAW deploys eight Helm charts through Argo CD. Some of those charts create cluster-wide shared services, while others are instantiated once per user. Let’s follow the same top-to-bottom flow as the diagram: shared services first, then the per-user fan-out, then what happens inside a single VM.

Shared services

Five namespaces host the components that every user VM depends on:

openshell-agents

The governance interceptor (a single-replica Deployment listening on gRPC port 18081), the governance policy and provider-profile ConfigMaps, and the golden-image DataSource that every VM clones its root disk from.

saw-keycloak

Red Hat build of Keycloak with the openshell realm. Keycloak issues OIDC tokens that the gateway validates, and it provides the login flow for both the CLI and the dashboard.

vault

HashiCorp Vault, deployed by the validated patterns framework. Vault stores inference credentials, SSH keys, and any other secrets the admin provisions per user.

external-secrets

The External Secrets Operator watches Vault and creates Kubernetes Secrets in each user namespace. This is how credentials travel from the admin’s Vault entries into the VM without the user (or the VM image) ever seeing Vault directly.

openshift-cnv

OpenShift Virtualization, which provides the VirtualMachine API that SAW uses to run one VM per user.

Per-user fan-out

The saw-users chart is the multiplier. For each user listed in overrides/saw-users.yaml, it creates a namespace saw-<name> and three Argo CD Applications:

  1. saw-<name>-secrets deploys the pattern-secrets chart, which creates ExternalSecret resources that pull the user’s credentials from Vault into Kubernetes Secrets.

  2. saw-<name>-bom deploys the saw-bom chart, which writes a ConfigMap containing the Bill of Materials (BOM) and the user’s profile definitions.

  3. saw-<name> deploys the openshell-saw chart, which creates the VirtualMachine, the Service, the Routes, and the in-guest installer configuration.

Everything a user needs lives in that single namespace, isolated from every other user by standard Kubernetes RBAC and network policy. If you have worked with other per-tenant patterns on OpenShift, this structure will look familiar: the fan-out chart is the control plane, and the per-user charts are the data plane.

Inside the VM

Each VirtualMachine clones its root disk from the golden-image DataSource in openshell-agents. The defaults give it 4 CPU cores, 8 GiB of memory, and a 40 GiB disk.

The golden image is a Fedora 44 cloud image customized with virt-customize. It contains Podman, Node.js, cloud-init, and the systemd units that drive the boot sequence. An image built from the baseline also contains cosign and the installer bundle verifier verify-bundle, while the prebuilt image that make copy-images mirrors at this baseline predates the verifier. The OpenShell gateway binary is not baked into the image. Instead, a systemd service runs the BOM installer at first boot, which pulls every OpenShell component by digest from the container registry. It copies the CLI, gateway, and supervisor binaries out of their images and installs them. The fourth component, the sandbox runtime image, stays an image: the gateway’s Podman driver mounts the sandbox binary from it into every sandbox it starts. This design means the admin controls exactly which versions run, through the BOM ConfigMap, without rebuilding the image. We cover the BOM in detail in BOM and profiles.

Once the boot sequence finishes, the VM runs three groups of processes:

OpenShell gateway (port 17670)

The gateway accepts gRPC connections from the openshell CLI and manages sandboxes. It uses its own CA for mTLS and validates OIDC tokens from Keycloak.

Dashboard and oauth2-proxy

The OpenShell dashboard runs as a Podman container inside the VM. An oauth2-proxy container sits in front of it, handling OIDC authentication so that users can open the dashboard in a browser without managing certificates.

Sandboxes

Each sandbox is a Podman container (OpenClaw, NemoClaw, or a custom image) that the gateway starts through its Podman driver. Next to each sandbox, the driver runs an OpenShell supervisor container that proxies the sandbox’s network traffic and adds credentials only where the policy allows. Sandboxes run under a restricted policy injected by the governance interceptor. In each OpenClaw and NemoClaw sandbox whose provider has an endpoint that the installer knows, the installer also starts the OpenClaw gateway, which serves the agent’s web UI on port 18789 inside the sandbox container.

SAW’s Route names are counterintuitive. SAW sets up the Route named dashboard for the OpenClaw agent UI, not for the OpenShell Dashboard. The Route named webui reaches the OpenShell Dashboard through oauth2-proxy.

The gateway Route uses passthrough TLS because the gateway performs its own mTLS handshake. The dashboard and web UI Routes use edge termination, so the OpenShift router handles TLS and forwards plain HTTP into the VM.

Why passthrough for the gateway? The gateway issues its own CA and client certificates, with the OU field carrying OIDC roles (openshell-admin or openshell-user). If the router terminated TLS, those client certificates would never reach the gateway, and the mTLS-based role check would break.

How a credential reaches an agent request

SAW keeps inference credentials away from the sandbox while still letting agents use them. Let’s trace the path a credential takes:

  1. The admin writes a credential into Vault (or the values-secret.yaml template populates it during install).

  2. The External Secrets Operator creates a Kubernetes Secret in the user’s namespace.

  3. The Secret is mounted into the VM as a disk or virtiofs share under /run/saw/secrets/<secretName>.

  4. The BOM installer reads the credential from that mount, registers it with the gateway as a named provider, and passes it through an environment variable, never on the command line.

  5. The installer’s Shell class masks every registered secret value in log output, replacing it with ***.

  6. Inside the sandbox, the agent holds only a placeholder key in the provider’s environment variable, such as NVIDIA_API_KEY, and calls the provider’s own endpoint with it. For OpenClaw, the installer sets that endpoint up, for example https://integrate.api.nvidia.com/v1 for NVIDIA.

  7. The sandbox proxy, run by the supervisor container, swaps the placeholder for the real key, but only on requests to the endpoints the provider profile allows and only from the binaries the profile lists. The sandbox process itself never sees the raw key.

At no point does the user, the sandbox, or the VM image contain a static copy of the credential. If the admin rotates a key in Vault, the External Secrets Operator propagates the change into the namespace, and on the next reconcile the installer picks up the new value.

This separation is deliberate. A sandbox runs untrusted agent code, so giving it direct access to an API key would make every sandbox compromise an immediate credential leak. Because the real key stays outside the sandbox and works only for the profile’s endpoints and binaries, a compromised sandbox can at most use those endpoints while it runs. It cannot walk away with the underlying key.
