What you can and cannot change

SAW separates what you can do on your own from what the admin controls. This page maps out those boundaries, explains what happens when you hit one, and shows how to request a change.

The change matrix

The following table shows who can perform each action across three tiers.

You alone

A plain openshell-user without workspace membership. This is the default when your admin leaves ownerSubject empty. The gateway rejects your CLI requests in the workspace, so you can’t list, connect to, or create sandboxes, and you can’t create providers.

With workspace admin

Your admin set ownerSubject in the SAW user configuration, which grants you workspace admin membership. You can create sandboxes, choose images, and register providers within governance limits.

Admin only

The action requires editing the SAW repository and pushing through GitOps.

What happens when you hit a boundary

When you attempt an action the governance interceptor does not allow, the gateway returns PERMISSION_DENIED with a reason from the interceptor. Typical reasons include:

  • "sandbox policy updates are blocked by provider profile governance" (you ran openshell policy update, which sends incremental changes to a sandbox policy, and the interceptor blocks every such change)

  • "sandbox policy must match the provider governance baseline" (the sandbox creation request carried a policy that doesn’t match the signed baseline)

  • "sandbox policy update governance annotations are stale" (the sandbox was created before an interceptor restart, and the signing key has changed)

openshell policy set replaces the whole policy instead. The CLI sends the new policy without the governance annotations that carry the interceptor’s signature, so the interceptor denies it with "sandbox policy updates must include governance annotations".

The gateway’s failure_policy for the interceptor is set to fail_closed, which means any interceptor failure (timeout, crash, or network partition) also blocks the operation rather than letting it through. The denial is intentional: it keeps a single admin-controlled policy baseline in effect across every gateway. See How governance works for the full explanation of how the interceptor enforces policy.

A provider type outside the governance profile list fails earlier, in the CLI, before the request reaches the interceptor. openshell provider create looks up the type’s profile first, finds none on the gateway, and prints:

provider profile '<type>' not found; import a matching profile before using this provider type

Importing a profile doesn’t help in SAW, because the gateway ignores imported profiles. Ask your admin to add the profile to the governance-policy chart instead. A client that sends CreateProvider to the gateway API directly skips the lookup and gets PERMISSION_DENIED from the interceptor, with the reason "providers may only use vended provider profiles".

How to request a change

If you need a capability that falls in the "Admin only" column, ask your SAW admin to make the change through the SAW Git repository. The admin follows one of these paths:

BOM profile change

To add a new sandbox definition, change an image, or adjust provider configurations, the admin edits the BOM profile files under charts/saw-bom/profiles/ and pushes a pull request.

Policy change

To modify network, filesystem, or process restrictions, the admin edits policy.yaml in the governance-policy chart and pushes a pull request.

User configuration change

To grant you workspace admin rights (so you can create sandboxes and providers yourself), the admin sets ownerSubject to your Keycloak subject UUID in overrides/saw-users.yaml and pushes a pull request.

After the pull request merges, Argo CD syncs the changes into the cluster. New sandboxes pick up the updated configuration at creation time. Running sandboxes keep their existing policy until they are destroyed and recreated.

Bring your own container image

Creating any sandbox, with a custom image or without one, requires workspace membership. If your admin has set ownerSubject for you, you are a member and can use the --from flag:

openshell sandbox create --from myregistry.com/my-image:tag

The --from flag takes a container image reference. It no longer builds a local Dockerfile or directory. Build and tag the image yourself, then push it to a registry that your gateway can pull from, because the gateway runs in your VM and not on your machine.

Your custom image must meet these requirements:

  • Declare a non-root OCI USER (a named account like app, a numeric UID with a passwd entry, or a numeric pair like 1500:1500). You can instead set process.run_as_user and process.run_as_group explicitly in policy.

  • Create and make writable a /sandbox directory for the workspace.

  • Install iproute2 for full network namespace isolation.

  • Use a standard Linux base image. Distroless and FROM scratch images are not supported.

  • Pass your start command after -- on the CLI. OpenShell starts the container with its own sandbox binary instead of the image’s CMD or ENTRYPOINT, and that binary launches your command. The OpenShell supervisor runs in a separate container next to the sandbox (see Where things run).

Even with a custom image, the governance interceptor injects the same signed policy and provider restrictions as with the default image. The interceptor governs policy and providers, not image choice.
