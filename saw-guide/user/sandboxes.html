Work with sandboxes

After connecting (see Log in and connect), your workspace already contains the sandboxes your admin configured through the BOM profile. This page shows you how to list them, connect, and open the web UIs.

List your workspaces and sandboxes

Your gateway organizes sandboxes into workspaces. The default BOM profiles create one or two workspaces, each with its own set of sandboxes.

List the workspaces you are a member of:

openshell workspace list

If the list is empty, you are not a member of any workspace yet. Run openshell whoami and send the value on its Subject: line to your admin.

List the sandboxes in the default workspace, which the CLI uses unless you pass --workspace or set OPENSHELL_WORKSPACE:

openshell sandbox list

Check: The output shows a table with the name, creation time, and phase of each sandbox.

To list sandboxes in a different workspace, use the --workspace flag:

openshell sandbox list --workspace cuda-dev

The cuda-dev workspace of the default data-science profile holds a nemoclaw sandbox, cuda-sandbox. The installer points nemoclaw onboard at your VM’s own OpenShell gateway, which the openshell-gateway service runs on the gateway port, and declares it as an externally supervised gateway. NemoClaw attaches to such a gateway only when it can confirm that the process on the gateway port belongs to the declared service and answers its health check. When it cannot, nemoclaw onboard stops in its first step, the preflight checks. It then reports "The externally supervised gateway attachment was rejected." and names the capabilities gateway.attachment.valid and gateway.port.uncontested. Even when the attachment passes, NemoClaw stops later in the same step if it keeps your VM’s openshell CLI, because the NemoClaw release that SAW installs declares a 0.0.x release as the highest OpenShell version it supports. Your VM runs OpenShell 0.1.2-rhaiv.0, which is newer. The preflight reinstalls the CLI before this check only in some cases, for example when it finds a development build. When either check stops nemoclaw onboard, the installer creates cuda-sandbox as a plain sandbox from its image and starts OpenClaw in it, without NemoClaw’s onboarding.

The --all-workspaces flag lists sandboxes across every workspace, but only for the platform admin role (openshell-admin). With the openshell-user role alone, the gateway rejects it.

Connect to a sandbox

To work inside a sandbox, open a shell in it with openshell sandbox exec:

openshell sandbox exec -n <sandbox-name> -- sh

The CLI runs sh in the sandbox container, where you can run agent commands, inspect files, or launch tools. When your input and output are a terminal, the CLI allocates a terminal for the shell, and --tty forces one. Type exit to leave the shell.

The CLI looks for the sandbox in the default workspace, so a sandbox in another workspace needs --workspace, for example openshell sandbox exec -n cuda-sandbox --workspace cuda-dev — sh. Without it, the CLI reports sandbox not found. If you omit the sandbox name, the CLI uses the last sandbox you worked with.

What sandbox connect does

openshell sandbox connect <sandbox-name> doesn’t start a new shell. It opens an SSH connection through the gateway and attaches your terminal to the sandbox’s main process, the command that the sandbox was created with. The installer creates every SAW sandbox with sleep infinity as its main process and without a terminal. In these sandboxes, connect therefore shows no prompt and no output, and it looks as if it hangs. Press Ctrl-C to leave. This ends only your connection, and the sandbox keeps running.

A sandbox that you create yourself from a terminal without a start command runs a login shell as its main process, so there connect gives you that shell. To leave it without ending the shell, press Ctrl-P followed by Ctrl-Q.

Open the OpenClaw web UI

In each OpenClaw and NemoClaw sandbox whose provider has an endpoint that the installer knows, such as the NVIDIA provider of the default profile, the installer starts the OpenClaw gateway. The OpenClaw gateway is the agent’s own server process, separate from the OpenShell gateway. It serves the agent’s web UI on port 18789 inside the sandbox, and you use that UI to send prompts to the agent from your browser.

The UI doesn’t use your Keycloak login. The OpenClaw gateway checks its own token, which the installer generates when it configures the sandbox and stores in the sandbox’s OpenClaw configuration. Read the configuration from the sandbox:

openshell sandbox exec -n <sandbox-name> --no-tty -- cat /sandbox/.openclaw/openclaw.json

The token is the token value in the gateway.auth section. The installer sets a new token each time it configures the sandbox, so read it again if the UI stops accepting the old one. Treat the token like a password, because anyone who has it can use the agent.

Forward the OpenClaw port (18789) from the sandbox to your machine:

openshell forward service <sandbox-name> --target-port 18789

Then open http://localhost:18789/#token=<token> in your browser, with the token you read above. For a sandbox outside the default workspace, such as cuda-sandbox, add --workspace <workspace> to both commands.

Your access checklist may also list the OpenClaw UI Route URL, the address of the Route named dashboard. That Route forwards to port 18789 of your VM, and the installer adds its address to the browser origins the OpenClaw gateway accepts. At this baseline the Route does not reach the OpenClaw UI, though. OpenClaw listens on port 18789 inside the sandbox container, and the sandbox container has no network of its own, so nothing connects the VM’s port 18789 to OpenClaw. Use the port forward above to open the OpenClaw UI.

The Route name dashboard is a SAW convention. SAW sets up this Route for the OpenClaw agent UI, not for the OpenShell Dashboard. See Architecture for the full Route table.

Open the OpenShell Dashboard

The OpenShell Dashboard provides a web-based overview of your gateway, workspaces, and sandboxes. Your admin exposes it through the Route named webui, fronted by oauth2-proxy for authentication.

Open the OpenShell Dashboard URL from your access checklist in your browser. You authenticate through the same Keycloak login flow as the CLI.

Where things run

When you work inside a sandbox, it helps to know what runs where.

The agent process (OpenClaw, NemoClaw, or your custom image) runs inside the sandbox container. The sandbox is a Podman container that the OpenShell gateway starts in your dedicated VM. Next to each sandbox, the gateway’s Podman driver runs an OpenShell supervisor container. The sandbox container has networking turned off, so all of its network traffic goes through the supervisor.

Inside the sandbox, DNS answers with addresses from 198.18.0.0/15 instead of the real ones. The sandbox proxy maps each of these addresses back to the host name. The policy then checks the name, the port, and the calling program, and decides whether the connection may go out. A name that the policy doesn’t allow can still resolve to such an address, but the connection to it is denied.

No web search in the default sandbox

The default notebook sandbox has only the NVIDIA provider attached. The SAW baseline policy allows no network destinations of its own, so the sandbox policy allows only the NVIDIA provider’s endpoint and the proxy denies every other host. When you ask the agent to search the web or to fetch a web page, these requests fail, while its model calls to NVIDIA keep working. To give the agent web search, your admin has to change the BOM profile, as described in How to request a change.

The agent never sees the real keys of its providers, such as NVIDIA Build, OpenAI, or Brave Search. It calls the provider’s endpoint directly with a placeholder key. The sandbox proxy swaps in the real key, but only for requests that go to the endpoints the provider profile allows and come from the binaries it lists. A compromised agent therefore can’t read the raw keys.

The sandbox policy, which controls network access, filesystem permissions, and provider allowlists, is injected and signed by the governance interceptor at creation time. You can’t change the policy from inside the sandbox. See Architecture for the full picture of shared services, per-user VMs, and credential flow.
