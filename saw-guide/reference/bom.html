BOM and profiles

The InstallerBOM resource defines which software versions the in-VM installer deploys. BOM profiles define the workspaces, providers, and sandboxes the installer creates after the binaries are in place.

InstallerBOM schema

The installer validates every BOM document against these rules (see apply_bom.py):

Field Constraint

apiVersion

Must be saw.redhat.com/v1alpha1.

kind

Must be InstallerBOM.

metadata.name

DNS label, maximum 63 characters.

spec.installerVersion

Must match the installer’s built-in INSTALLER_VERSION constant. A mismatch is a hard error.

spec.openshell

Required. Exactly four components: cli, gateway, supervisor, and sandbox. A missing or unknown component is an error. All four must carry the same version; the comparison ignores a leading v and treats + and - alike.

spec.openshell.cli

Required. version (semantic version string) and image (container reference pinned by digest). Optional: path (absolute path to the binary inside the image, default /usr/local/bin/openshell), signature (keyRef or identity/issuer for verification). The installer copies the binary out of the image.

spec.openshell.gateway

Required. Same structure as cli. Default path: /usr/local/bin/openshell-gateway.

spec.openshell.supervisor

Required. Same structure as cli. Default path: /openshell-supervisor. The chart also writes this image into the gateway configuration as the Podman driver’s supervisor_image.

spec.openshell.sandbox

Required. The sandbox runtime image, with version, a digest-pinned image, and an optional signature. The installer pulls this image but extracts no binary from it. The chart writes it into the gateway configuration as sandbox_runtime_image, and the gateway’s Podman driver mounts the static openshell-sandbox binary from it read-only into every sandbox container.

spec.nemoclaw.cliImage

Optional. A tag is accepted with a warning; a digest pin is recommended.

All four OpenShell components must have images pinned by digest. Tags are refused because a tag can move and the BOM would stop describing what is installed. The installer checks image signatures for all four components when signing is enabled.

Profile layout

Profiles live under charts/saw-bom/profiles/<profile>/<workspace>/. Each workspace directory contains up to three YAML files:

workspace.yaml (kind: Workspace)

Metadata for the workspace, including its name and description. A workspace named default maps to the gateway’s built-in workspace.

providers.yaml (kind: Providers)

List of provider entries under spec.providers. Each provider needs name, type, and credentialSecret. Optional fields: credentialSecretKey (default api_key), enabled (default true), model, nemoclawProvider, baseUrlSecretKey, modelSecretKey, inferenceTimeout. Only the openai, anthropic, and nvidia types accept baseUrlSecretKey. The installer still accepts inferenceTimeout but does not use it, because OpenShell has no gateway inference router to apply a timeout to.

sandbox.yaml (kind: Sandboxes)

List of sandbox entries under spec.sandboxes. Each sandbox needs a name (DNS label, at most 19 characters). Optional fields: type (default generic), enabled (default true), image, agent, providers, model. An openclaw or nemoclaw sandbox needs at least one enabled provider in its workspace.

The saw-bom chart flattens these files into a ConfigMap (saw-bom-profiles) with keys like profiles__data-science__default__workspace.yaml. The in-VM installer parses them back into the profile/workspace/file hierarchy.

An accepted type does not mean the gateway can create the provider. OpenShell v0.1.2 has no built-in provider profile catalog and rejects a builtin profile source, so a provider type works only if a profile with that id exists. With governance on, the profiles come from the governance catalog (see Governance provider profiles), which covers brave, gemini, nvidia, and openai from this table. With governance off, the installer imports the profile bundled with the openshell-saw chart for brave, nvidia, or openai when the gateway lacks one. In either mode, the installer skips any other provider with a warning, because the CLI finds no profile for its type and never sends the CreateProvider request. An openclaw or nemoclaw sandbox whose listed providers were all skipped fails the installer’s verification, and the apply step ends with status Failed.

For an OpenClaw sandbox, the installer configures the agent with its provider’s own endpoint: the base URL the provider reads from its Secret, or else https://integrate.api.nvidia.com/v1 for the nvidia and build types and https://api.openai.com/v1 for openai. For any other type without a base URL, the installer skips OpenClaw onboarding and logs a warning.

Sandbox types

The SANDBOX_TYPES set defines the valid sandbox type values: generic, openclaw, and nemoclaw.

Shipped profiles

Two profiles ship with the baseline:

data-science (default)

Workspace default

NVIDIA (type nvidia) and Brave (type brave) providers. One openclaw sandbox (notebook), one disabled nemoclaw sandbox (cuda-sandbox), one disabled generic sandbox (toolbox). All three sandboxes list only the nvidia provider, so no sandbox attaches the brave provider. The installer still requires the brave credential from the Secret web-search, and the apply step fails without it.

Workspace cuda-dev

NVIDIA (type nvidia) provider. One nemoclaw sandbox (cuda-sandbox), one disabled generic sandbox (toolbox).

custom-inference

Workspace default

An openai-type provider (custom) that reads the base URL and model from the inference Secret, plus a Brave (type brave) provider. One openclaw sandbox (notebook), which lists only the custom provider. As in data-science, no sandbox attaches the brave provider, but the installer requires its credential.

The agent calls the base URL directly, so the openai governance profile must name that server’s host and port. The shipped openai profile allows only api.openai.com (see Governance provider profiles). SAW’s custom inference documentation lists this setup as not yet verified end to end with the OpenShell release the BOM installs.

Governance provider profiles

Seven provider profiles ship in charts/governance-policy/profiles/. The governance interceptor loads them at startup and reloads on ConfigMap changes. A BOM provider’s type names the profile id it uses, and the profiles carry no separate provider_type field. If the type matches no loaded profile id, the interceptor denies the CreateProvider request.

Each profile lists the endpoints its provider may reach and, under binaries, the executables in the sandbox that may use them. The agent holds only a placeholder for the credential. The sandbox proxy replaces it with the real credential only on requests to a listed endpoint from a listed binary. A missing or empty binaries list allows nothing. See Provider profiles follow the ConfigMap for how the gateway uses the profiles.

In the table, curl, gh, and git stand for the binary in both /usr/bin and /usr/local/bin. node stands for /usr/bin/node, /usr/bin/node-*, and /usr/local/bin/node. In the Hummingbird image that OpenClaw runs in, /usr/bin/node links to /usr/bin/node-<major>, and the rule matches the real path. The NemoClaw image uses /usr/local/bin/node.
