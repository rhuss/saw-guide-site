Experimental and upcoming features

The pull requests described on this page were in review against the SAW repository at the time of the baseline (2026-10-02). None of them are part of the baseline commit that the rest of this guide documents. They may change significantly, be reworked, or be dropped before they merge.

Nothing on this page is an instruction. The sections below describe intent only, so you can understand what each change would mean for your deployment if it lands. Where a feature would affect admin or user workflows, those effects are noted, but no steps are provided because the implementation is not final.

Self-service portal with Red Hat Developer Hub

Experimental: in review

Self-service portal with Red Hat Developer Hub is not part of the baseline. It is proposed in PR #57 (status as of 2026-10-02) and may change or be dropped before it merges. This section describes intent only.

This PR lets users create their own workspace from Red Hat Developer Hub (RHDH). It replaces the earlier PR #33, whose pipelines installed each sandbox with Helm. PR #57 builds workspaces the same way SAW already does for users declared in Git: through the saw-users chart.

A user signs in to RHDH with their Keycloak account, picks a SAW-BOM profile, and enters only the API keys that profile needs. The result is the namespace saw-<user> with a VM and the profile’s sandboxes, the same set an admin gets from an entry in overrides/saw-users.yaml. Nothing is written to Git. The keys go to Vault under the user’s own saw-<user> path in the hub prefix, and the workspace becomes an entry in an in-cluster registry, a ConfigMap in the new saw-portal namespace.

The new openshell-rhdh chart deploys RHDH with two templates, one to create a workspace and one to delete it. Each request starts an OpenShift Pipelines (Tekton) pipeline in saw-portal, which checks the form and writes the keys and the registry entry. The pipeline then waits for each stage of the build, so the user can follow the progress in RHDH. Argo CD still does the building. An ApplicationSet asks a small generator service for the registry entries and creates one Application per user, which renders the saw-users chart for that one user. The ApplicationSet only creates and updates Applications, so a registry problem never deletes a VM; deleting is the delete pipeline’s job.

The pipeline doesn’t trust anything the form says about who the user is. RHDH puts the user’s Backstage token, a signed JWT, into each request. The pipeline checks the token’s signatures and expiry against the keys RHDH publishes and takes the user name from the token’s subject. A user can therefore create or delete only their own workspace. The pipeline also refuses a user who is already declared in Git, and a workspace whose Argo CD applications would collide with someone else’s.

The permissions behind the portal are narrow. RHDH’s service account may only create request Secrets and start the two portal pipelines in saw-portal, and admission policies pin exactly what it may create there. The pipeline’s service account holds Roles only in saw-portal and the Argo CD namespace, plus read access to namespaces and VMs. An admission policy lets it delete only the Applications the portal created. It never writes to a user’s namespace, because Argo CD builds everything in it. Its Vault role can write to every portal user’s path, so only the token check keeps a request away from other users' keys. In RHDH itself, role-based access shows each user only their own workspace and only the actions that apply to them.

The PR reaches beyond the portal in two places. Any sandbox can set ui: {route: true} in its SAW-BOM profile to get its own Route to the agent’s web UI, for portal users and Git-declared users alike. An oauth2-proxy in the VM signs the user in with Keycloak and admits only the workspace owner and any users the admin allows. OpenClaw trusts that sign-in, so the browser needs no gateway token. Keycloak also gets stricter: test users get generated passwords instead of defaults, self-registration is off, and the realm enforces a password policy and locks accounts after repeated failed sign-ins.

For admins, onboarding changes from editing overrides/saw-users.yaml for every user to creating Keycloak accounts and letting users request their own workspaces. Because self-registration is off, a user can reach the portal only after an admin creates the account. Admins named in the chart’s portal.admins value also get templates to create or delete a workspace for another user. The pattern would install the portal by default, together with the OpenShift Pipelines operator and an imperative job that creates the pipeline’s Vault role. An existing deployment would need two new generated entries in its secrets file. Each VM would also need a restart before its sandbox UI Routes work, because the Routes add VM interface ports.

For users, the portal replaces waiting for an admin hand-over. A user fills in a form, follows the progress, and then finds the workspace in the RHDH catalog with links to the OpenShell web UI and to each sandbox UI. Creating and deleting a workspace needs neither cluster access nor the OpenShell CLI.

Watch for: at the recorded head, the PR hadn’t yet tested the full flow from the RHDH form to a running workspace, or the delete flow, on a cluster. It had checked the Keycloak changes, the sandbox UI sign-in, and the RHDH resource definition live.

GPU passthrough

Experimental: in review

GPU passthrough is not part of the baseline. It is proposed in PR #37 (status as of 2026-10-02) and may change or be dropped before it merges. This section describes intent only.

This PR wires GPU passthrough from the host through KubeVirt into the sandbox container. It adds a vm.gpu block to the openshell-saw chart values, rendered as a conditional hostDevices entry on the VirtualMachine spec, and a matching pciHostDevices entry in the openshift-cnv chart for the HyperConverged resource.

The golden image build gains an optional NVIDIA Container Toolkit layer. When enabled, a first-boot systemd service compiles the kernel module against the running kernel and generates the CDI spec that Podman needs to pass the GPU into a sandbox container. BOM profiles can declare GPU requirements per sandbox (gpu: {enabled: true, count: 1}), and the installer passes those through to openshell sandbox create.

Everything defaults to off. Existing deployments that do not set vm.gpu.enabled see no change in chart rendering or VM behavior.

For admins, GPU passthrough requires bare-metal nodes (or a cloud platform that exposes IOMMU groups to the guest), the NVIDIA GPU Operator, and a HyperConverged configuration that maps the PCI device. The PR’s own testing found that nested virtualization on AWS g5.2xlarge instances does not expose the necessary hardware extensions, confirming that the feature targets physical hardware.

For users, sandboxes with GPU access would work the same as regular sandboxes, with the addition of GPU device visibility inside the container. The --gpu flag on openshell sandbox create is a native OpenShell feature, so no SAW-specific CLI changes are needed.

Choosing between the governance interceptor and APF

Experimental: in review

Choosing between the governance interceptor and APF is not part of the baseline. It is proposed in PR #52 (status as of 2026-10-02) and may change or be dropped before it merges. This section describes intent only.

This PR adds a toggle in values-global.yaml that lets the admin choose which service governs every SAW gateway: the existing OpenShell governance interceptor (the default) or NVIDIA Agent Policy Fabric (APF).

With global.governance.engine set to apf, the governance interceptor Deployment is replaced by an Argo CD Application that pulls the APF chart from a private OCI registry. APF serves the same policy files from charts/governance-policy, but delivers them as a signed bundle with provenance stamping and an audit trail. The Service name and port stay the same (governance-interceptor.openshell-agents.svc:18081), so gateways keep their endpoint. Switching the engine still re-renders every SAW gateway configuration with APF’s bindings, so each user VM restarts once.

A companion script (apf-bundle.py) translates the existing governance policy into APF documents and signs them with a locally generated seed. Only seed holders can change policy, which means a Git push to charts/governance-policy without a re-signed bundle would fail.

For admins, the switch requires access to the private APF chart and images on GHCR, a GitHub token with read:packages, and Vault entries for the pull credentials and signing seed. The default rendering for the interceptor engine is byte-identical to the current baseline, so switching to APF is opt-in and reversible by changing a single value.

For users, the governance engine behind their gateway is transparent. Sandbox creation, provider registration, and policy enforcement work the same regardless of which engine the admin chose.

Watch for: the APF image package access was still pending at the recorded head, so not all bindings and catalog behavior had been validated end to end. The PR pins APF chart version 0.2.0, which its own documentation says was built against OpenShell 0.0.x and isn’t verified with the 0.1.x gateways of this baseline. A 0.1.x gateway negotiates the extension protocol with its interceptor at startup and doesn’t start when the interceptor doesn’t speak it (see Interceptor and gateway versions). APF therefore needs a release built for OpenShell 0.1.x. Per-user policy and Cedar rules are explicitly out of scope for this PR.

Harness bundles

Experimental: in review

Harness bundles is not part of the baseline. It is proposed in PR #53 (status as of 2026-10-02) and may change or be dropped before it merges. This section describes intent only.

This PR delivers OpenClaw harness bundles (skills, MCP servers, and tool plugins) through the versioned SAW-BOM plane, mounted read-only at /sandbox/harness inside each sandbox.

A harness bundle can come from one of two sources. An OCI image built from the harness-bundles/ directory and published to GHCR is pulled by digest, and that digest is what the installer trusts. An inline bundle lives in charts/saw-bom/harness/ and ships in the profiles ConfigMap, which limits its size and file names and keeps no file modes. Either way, the installer copies the bundle unchanged into a Podman volume that belongs to the sandbox, and the sandbox mounts that volume read-only. No shell handles bundle content, and nothing is copied into the sandbox through sandbox exec.

The volume follows the mount rules of the OpenShell 0.1.x gateways in this baseline. With resource admission on, the gateway refuses image mounts and attaches a volume only when it carries labels for the sandbox’s workspace, which the installer sets. The gateway must also accept driver configuration from the caller, so the PR turns on allowDriverConfig in the openshell-saw chart by default, while bind mounts stay off.

A bundle never holds a key. An MCP server or tool plugin that calls a keyed service names a governance profile in harness.yaml, and the sandbox needs a provider of that type. The sandbox then sees only the provider’s placeholder, and the sandbox proxy swaps in the real key on requests to the profile’s endpoints, as it does for model keys. An earlier revision of the PR exported a real key into the OpenClaw gateway process inside the sandbox, where the agent could read it. That path is gone, and the installer now refuses the credentialSecret, credentialSecretKey, and credentialEnvVar fields.

Before it writes anything, the installer checks each bundle against the provider profiles the gateway serves for the sandbox’s workspace. The gateway must serve every governance profile the bundle names, the sandbox must have a provider for it, and a remote MCP server’s host must be one of that profile’s endpoints.

For admins, harness bundles become part of the BOM profile. Adding or updating a bundle means editing the profile’s sandbox.yaml to reference a new digest or inline bundle name, then pushing through Git. An update refills the volume in place and keeps the running sandbox. Adding a bundle to a running sandbox, or removing one, recreates that sandbox, so anything the agent wrote outside /sandbox/persist and other data volumes is lost.

For users, harness content appears at a fixed path inside the sandbox. The bundle’s skills, tools, and MCP servers are available to OpenClaw without any manual setup.

The PR also hardens the installer’s start_openclaw function. It quotes the OpenClaw profile ID, the gateway token it writes into the OpenClaw configuration, and the dashboard origin before it passes them to a shell inside the sandbox.

Watch for: the PR description still shows the earlier image mounts and credentialSecret path, while this section follows the code at the recorded head. At that head, the PR reports end-to-end checks on OpenShell 0.1.2-rhaiv.0 for both bundle sources. Reaching an in-cluster MCP Service from inside a sandbox was still open, because OpenShell’s default sandbox network policy denies it.

Agent identity with SPIFFE and SPIRE

Experimental: in review

Agent identity with SPIFFE and SPIRE is not part of the baseline. It is proposed in PR #55 (status as of 2026-10-02) and may change or be dropped before it merges. This section describes intent only.

This PR replaces static API keys with short-lived, sandbox-bound tokens issued through SPIFFE/SPIRE workload identity. It is marked as a draft and has significant work remaining.

Three new components are introduced. The spire-identity chart deploys the ZTWIM operator with SPIRE server, agents, CSI driver, and OIDC discovery. A Go registrar controller watches labelled VMs, creates bootstrap Secrets, and manages SPIRE registration entries. An optional identity-demo chart validates grants end to end.

Inside the guest, a digest-pinned SPIRE agent is delivered as a BOM component. The installer configures systemd units, a Workload API socket, persistent SELinux contexts, and credential reuse across reboots. Each sandbox receives a distinct SPIFFE ID, and the gateway issues tokens through OpenShell’s client_credentials and token_exchange grants instead of static keys.

The TCP client-credentials path is working on a live canary deployment. Token exchange, VSOCK transport, full pattern deployment through ./pattern.sh make install, and several isolation and lifecycle tests remain open. A known blocker is that the pinned OpenShell supervisor’s audit events do not carry the injected identity claims, which blocks audit acceptance.

For admins, enabling agent identity would mean deploying the SPIRE infrastructure alongside SAW and configuring spiffe.* values in the chart. For users, the token lifecycle would be invisible: the sandbox obtains and refreshes credentials automatically.

Planned without a pull request

Several features are planned but do not yet have a pull request in the SAW repository.

A RHEL-based golden image would replace the current Fedora base for the gateway VM. The motivation includes compatibility with the NVIDIA GPU Operator, which requires RHEL or a RHEL-derivative kernel for its driver toolkit.

Centralized log collection would aggregate logs from gateway VMs and sandbox containers into a cluster-level logging stack. The design direction is OCSF normalization, which would give security teams a structured format for analyzing agent activity across all workspaces.

Vault integration for OpenShell provider credentials would let the gateway resolve secrets directly from Vault instead of relying on the current flow where the External Secrets Operator syncs them into Kubernetes Secrets. The pattern-secrets chart already deploys Vault and ESO for the platform layer, so this would extend that path into the guest.

None of these items have committed timelines. They represent directions the project is working toward, based on upstream community discussions and published pull requests.
