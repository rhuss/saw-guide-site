Benefits and challenges

The previous pages walked through how SAW components fit together and how governance enforces a single policy across every gateway. This page steps back from the mechanics and looks at what those design choices buy you, and what they cost. If you are evaluating SAW for your environment, this is the page to read before committing to an install.

Benefits

Each benefit below maps to a design decision covered in the earlier Concepts pages. We keep the descriptions short here and link back to the details.

Dedicated VM per user with sandbox isolation

Every user gets their own VirtualMachine running its own OpenShell gateway. Sandboxes inside that VM are Podman containers, so a compromised agent process is contained by both the container boundary and the VM boundary. One user’s workload cannot reach another user’s namespace, credentials, or sandbox processes.

Credentials never inside the sandbox

Inference API keys travel from Vault through the External Secrets Operator into the VM, where the installer registers them with the gateway as providers, but they never enter the sandbox container itself. The agent holds only a placeholder key, and the sandbox proxy swaps in the real key only for requests to the endpoints its provider profile allows, from the binaries the profile lists. While the sandbox boundary holds, a compromised agent sees only placeholders, never the real key (see the credential path).

This protection is only as strong as the sandbox boundary. Inside a user’s VM, the components that hold the real credentials (the gateway, its encrypted credential store, and the supervisor that injects keys) run under the same account as the sandbox containers and share the VM’s kernel. So the boundary between the agent and the credentials is the container boundary, not a hypervisor one: the per-user VM separates one user from another, not the agent from its own keys. For many deployments this is a reasonable trade-off, because the sandbox only ever holds a placeholder, the proxy injects the real key per request, policy limits where that key can be used, and the per-user VM keeps the blast radius of an escape to a single user. If your threat model requires the credentials to stay protected even after a sandbox escape, consider a design that places a hypervisor boundary between the agent and the credentials, for example running the sandboxes through OpenShell’s Kubernetes driver with a Kata Containers runtime, where each sandbox gets its own lightweight VM and the gateway, supervisor, and credentials run outside it.
One admin-owned governance point that fails closed

A single governance interceptor enforces the same sandbox policy, provider allowlist, and credential-injection rules across every user gateway. If the interceptor is unreachable, the gateway blocks the operation rather than letting it through. The governance page covers the full enforcement flow.

Everything declarative in Git

Adding a user, changing a policy, or updating the Bill of Materials is a Git commit. Argo CD reconciles the change into the cluster, so there is no imperative drift between what the admin intended and what is running.

Verifiable installer bundle with digest-pinned components

The BOM pins every OpenShell component by container image digest, not by tag. A golden image built from the baseline contains cosign and the bundle verifier verify-bundle, and it can pin a signing-mode floor. With a signed bundle, the in-guest installer then checks bundle integrity before it installs anything. Bundle verification works only with such an image, because the prebuilt image that make copy-images mirrors at this baseline predates verify-bundle. The chart at this baseline ships no signed bundle either, so you also sign the bundle yourself and add your public key to the image. The manual install page shows how to build the image.

Choice of harness

SAW does not lock you into a single agent harness. The default BOM profile includes both OpenClaw and NemoClaw sandboxes, and you can bring your own container image if neither fits.

Challenges and drawbacks

Every system has trade-offs. We list each challenge with a brief explanation of why it matters and a pointer to where the guide addresses it.

Single-replica interceptor is a single point of failure

The governance interceptor runs as a single-replica Deployment. If the Pod is evicted, rescheduled, or crashes, every gateway loses its policy enforcement endpoint until the replica recovers. The fail-closed design means operations are blocked during the outage rather than running without governance. See Day 2 operations for monitoring and recovery guidance.

Policy changes do not reach running sandboxes

When the admin updates policy.yaml in Git, the interceptor re-signs it and applies it to every new sandbox. Sandboxes that are already running keep the policy they were created with because the interceptor’s reload push targets 127.0.0.1 inside its own Pod and never reaches the user VMs. You must destroy and recreate a sandbox to pick up a policy change. The governance page explains the mechanism in detail.

BOM changes restart the VM unless liveInputs is enabled

The default value of vm.liveInputs is false, which means the BOM ConfigMap is mounted as an iso9660 disk. Changing a BOM component or a provider credential requires a VM restart to take effect. Setting liveInputs to true switches to virtiofs, which makes changes visible without a restart, but that setting itself requires recreating the VM. See Day 2 operations for the operational procedure.

One VM per user plus bare metal or supported cloud platform

Each user consumes 4 CPU cores, 8 GiB of memory, and 40 GiB of disk by default, on top of 8 cores and 16 GiB for cluster overhead. OpenShift Virtualization requires bare metal nodes or a supported cloud platform, so check the compatibility list before planning your deployment. The prerequisites page covers sizing in detail.

One gateway per namespace with no per-gateway admin groups

Every user namespace contains exactly one gateway, and there is no mechanism to give different admin groups control over different gateways. All governance flows through the single interceptor in openshell-agents, which the cluster admin controls. If your organization needs per-team delegation, you will need to run separate SAW installs. SAW does not provide a workaround for this at the baseline.

The Fedora golden image is not a supported product

The VM runs a Fedora 44 cloud image customized with virt-customize. Fedora is a community project with a roughly 13-month lifecycle per release, and Red Hat does not provide commercial support for it. If your security policy requires a supported operating system, you will need to build your own golden image. SAW does not ship an alternative base image at the baseline.

Downstream OpenShell pin and upstream API churn

SAW pins OpenShell at version 0.1.2-rhaiv.0, a downstream build of the upstream v0.1.2 release. OpenShell has not reached 1.0, and SAW’s installer treats every new minor release as a breaking one. The move to the 0.1 series, for example, recreated every sandbox and removed managed inference routing. Upgrading means testing against those changes and moving the governance interceptor to the same release. See Day 2 operations for upgrade guidance.

User and sandbox names are limited to 19 characters

The saw-users chart validates that each user name is a lowercase DNS label of at most 19 characters. This limit comes from OpenShell’s VirtualMachine naming rules and the Route labels derived from them. Names that are too long or that contain uppercase letters fail at Helm render time. The GitOps install page and manual install page note this constraint where you first define user names.

Operators installed but unused

The validated patterns framework subscribes to Red Hat Developer Hub and OpenShift AI operators through values-prod.yaml, but SAW does not deploy any applications for them. These subscriptions consume cluster resources (CRDs, operator Pods, memory) without providing functionality. You can remove them from your fork if you do not plan to use them. SAW provides no toggle for this at the baseline; editing the fork is the only option.

Defaults ship with known credentials

The Keycloak chart creates test users with known passwords (developer/developer, admin/admin, alice/alice, bob/bob), enables self-registration, and sets the PostgreSQL password to keycloak-db-pass. These defaults are convenient for a lab but dangerous on any cluster reachable from outside your network. See GitOps install and manual install for the security warnings, and what you can change for how users interact with the defaults.
