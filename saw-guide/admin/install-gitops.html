Install with GitOps

Baseline

This guide describes SAW at commit 4768f02 (2026-10-02), which deploys OpenShell 0.1.2-rhaiv.0. Later SAW commits may rename targets or change defaults.

The GitOps path uses the validated patterns framework to deploy SAW in a single command. The framework reads values-global.yaml and values-prod.yaml from your repository, loads your secrets into Vault, and creates Argo CD Applications for every SAW component. From that point on, Argo CD keeps the cluster in sync with your fork: push a change, and the cluster converges to match.

Before you begin, confirm that every item on the Prerequisites and sizing page is in place. You need cluster-admin access, the CLI tools listed there, and enough capacity for at least one user VM plus the shared-services overhead.

Steps

  1. Fork and clone the repository.

    Fork validatedpatterns-sandbox/secure-agent-workspace to your own GitHub organization, then clone your fork. The validated patterns framework pushes the current branch to the remote, so the repository must be one you can push to.

    git clone https://github.com/<your-org>/secure-agent-workspace.git
cd secure-agent-workspace

  2. Check out the baseline commit.

    This guide is written against a specific SAW commit. Checking it out ensures that every command on this page matches the code you are running.

    git checkout 4768f02d4415449de74403df62bad0c03630448e

  3. Log in to OpenShift with cluster-admin.

    The install target creates namespaces, operator subscriptions, and cluster-scoped resources, all of which require cluster-admin privileges.

    oc login --server=https://api.<cluster>:6443 -u <user>

    Check: Confirm that you are logged in and that whoami returns a cluster-admin user.

    oc whoami

  1. Generate SSH keys.

    The make generate-keys target creates an Ed25519 keypair under ~/.generated-ssh-keys/sandbox-ssh. SAW injects the public key into every user VM so that virtctl ssh works without a password. The target also copies values-secret.yaml.template to ~/values-secret.yaml if no secrets file exists yet.

    make generate-keys

    Check: Confirm that the keypair exists.

    ls -l ~/.generated-ssh-keys/sandbox-ssh*

  2. Configure secrets.

    The make generate-keys target already copied values-secret.yaml.template to ~/values-secret.yaml. If the file does not exist, copy it manually:

    cp values-secret.yaml.template ~/values-secret.yaml

    Edit ~/values-secret.yaml and provide values for each group:

    ssh

    Already populated by make generate-keys. The private_key and public_key fields point at ~/.generated-ssh-keys/sandbox-ssh and its .pub counterpart.

    inference

    Set provider, model, and the path to your API key file. The default profile expects an NVIDIA key at ~/.nvidia-api-key with provider: build and model: nvidia/nemotron-3-super-120b-a12b. Change the provider and model if you use a different inference backend (see the commented examples in the template).

    web-search

    Set provider and the path to your API key file. The default profile expects a Brave Search key at ~/.brave-api-key with provider: brave.

    The template also shows how to add per-user Vault prefixes. Each prefix goes under vaultPrefixes with a path relative to secret/data, for example hub/saw-alice, and lets one user override the shared inference or web-search key.

  3. Edit the user list.

    Open overrides/saw-users.yaml and add or remove entries. Each entry needs a name and a list of profiles. The repository ships with a single user:

    users:
  - name: alice
    profiles:
      - data-science

    Argo CD creates one namespace (saw-<name>) and three Application objects per user. Removing an entry prunes that user’s Applications.

    Check: Confirm the file is valid YAML.

    yq '.' overrides/saw-users.yaml

  4. Commit and push to your fork.

    The validated patterns framework reads from the remote branch, not from your working tree. Any local changes (your edits to overrides/saw-users.yaml and any other files you changed) must be pushed before the install. pattern.sh forwards TARGET_BRANCH and TARGET_ORIGIN to the utility container, and the deploying branch must exist on the remote.

    git add overrides/saw-users.yaml
git commit -m "Configure SAW for my cluster"
git push origin HEAD

  5. Copy pre-built images to the cluster.

    The golden VM image that every user VM clones its root disk from is hosted on quay.io/rh-ai-quickstart. make copy-images mirrors it into the cluster’s internal registry so that DataVolumes can reference it locally. The target asks quay for the tag in OPENSHELL_VERSION, then for the same tag with a v prefix, and otherwise falls back to latest. It stores the image it finds under the OPENSHELL_VERSION tag and also tags that image latest. This takes about five minutes.

    make copy-images

    Check: Confirm the ImageStream exists in the openshell-agents namespace.

    oc get imagestream -n openshell-agents
    The mirrored image has no bundle verifier

    At this baseline, quay has no golden image under the 0.0.x tag in OPENSHELL_VERSION or its v-prefixed form, so make copy-images mirrors latest. That image was built before SAW added the installer bundle verifier, verify-bundle. On boot, saw-stage-installer logs verify-bundle is not in this golden image; staging without verification. In the default warn signing mode the VM installs anyway, and in enforce mode the install stops.
    Building the golden image deletes the current one

    To get the bundle verifier, build the golden image from the baseline with make build-gateway-podman instead of running make copy-images. The target first deletes the golden DataVolume openshell-gateway-golden, its PVC, the openshell-gateway DataSource, the earlier builds of the image, and the openshell-gateway ImageStream. It then builds the image in the cluster, creates the golden DataVolume and DataSource from it, and pushes the image to QUAY_REPO as latest and as the OPENSHELL_VERSION tag. The default QUAY_REPO is quay.io/rh-ai-quickstart, so log in to a registry where you can push images and set QUAY_REPO to your organization there:

    podman login quay.io
make build-gateway-podman QUAY_REPO=quay.io/<your-org>

    Even a golden image built this way records the bundle as unsigned at this baseline, because the chart ships no signed bundle.sigstore.json. Verification also needs your public key in /etc/saw/trust, which the image build does not add.

  6. Run the install.

    pattern.sh launches make install inside the validated patterns utility container (quay.io/validatedpatterns/utility-container). It recommends podman newer than 4.3.0 and refuses to run with versions 1.5 and 1.6.

    ./pattern.sh make install

    The command takes several minutes. It installs the Argo CD operator (if not already present) and loads your secrets into Vault. Then it creates the seven Argo CD Applications defined in values-prod.yaml.

    Check: After the command finishes, confirm that all seven Applications appear and are synced.

    oc get applications.argoproj.io -n vp-gitops

What Argo CD creates

The framework creates seven Argo CD Applications plus operator subscriptions for ESO, OpenShift Virtualization, Red Hat build of Keycloak, Red Hat Developer Hub, and OpenShift AI. The seven Applications are:

  1. openshift-external-secrets (namespace external-secrets)

  2. vault (namespace vault, chart hashicorp-vault)

  3. openshift-cnv (namespace openshift-cnv)

  4. openshell-keycloak (namespace saw-keycloak)

  5. saw-users (namespace openshell-agents, reads overrides/saw-users.yaml)

  6. governance-policy (namespace openshell-agents)

  7. governance-interceptor (namespace openshell-agents)

Each user entry in overrides/saw-users.yaml causes the saw-users Application to create three child Applications in the Argo CD namespace. Those children are saw-<name>-secrets, saw-<name>-bom, and saw-<name> (the VM). For the shipped default (alice), you should see a VirtualMachine named alice in namespace saw-alice.

Check: Verify that the user VM exists and is running.

oc get vm -A

Vault

The vault Application deploys the hashicorp-vault chart (version 0.1.*) into the vault namespace. The chart itself is provided by the validated patterns framework, not by the SAW repository. Vault configuration details such as dev mode, storage backend, persistence, and unsealing strategy are managed by the framework. See the validated patterns secrets management documentation for how the framework configures and unseals Vault.

Change the defaults before exposing the cluster

The openshell-keycloak chart ships with test defaults that are not safe for production.

Test users with passwords equal to their names

The testUsers list in charts/openshell-keycloak/values.yaml creates four users: developer/developer, admin/admin, alice/alice, and bob/bob. To change these passwords, override keycloak.testUsers in your fork’s charts/openshell-keycloak/values.yaml or remove the test users entirely and create accounts through the Keycloak admin console.

Self-registration enabled

registrationAllowed: true lets anyone with access to the Keycloak login page create their own account. Set keycloak.registrationAllowed to false in charts/openshell-keycloak/values.yaml before you expose the cluster.

PostgreSQL password

The database password for Keycloak’s PostgreSQL instance defaults to keycloak-db-pass (postgres.password in charts/openshell-keycloak/values.yaml). Override postgres.password in your fork before deploying.

Next step

Once all Applications are synced and the user VM is running, proceed to Onboard users to hand over access credentials to your users.
