Day 2 operations

Once SAW is running, you’ll need to adjust governance profiles, rotate provider credentials, upgrade OpenShell versions, or remove users. Every change in this guide follows the same pattern: edit a Helm value or a file in Git, sync the chart, and let the in-guest installer handle the rest. The lifecycle diagram below shows the two update paths (default restart and live reconcile) that determine how quickly a change takes effect.

Figure 1. The VM lifecycle: boot sequence (top), default update path with VM restart (middle), and live reconcile with vm.liveInputs (bottom).

Change governance profiles

The governance interceptor reads provider profiles and policy.yaml from ConfigMap volumes. When you push a change to the governance-policy chart in Git, Argo CD syncs the updated ConfigMap. Kubelet propagates the new files into the interceptor Pod, typically within about 60 seconds. The interceptor picks them up on the next evaluation without a restart.

For the full governance flow, see How governance works.

Change the sandbox policy

Updating policy.yaml affects only new sandboxes. Running sandboxes keep their signed policy revision until they are destroyed and recreated. The interceptor’s reload push targets 127.0.0.1 inside its own Pod and never reaches the user gateways.

To bring existing sandboxes onto a new governance-policy:

  1. Edit policy.yaml in the governance-policy chart and push to Git.

  2. Wait for Argo CD to sync (about 60 seconds for the ConfigMap to propagate).

  3. Delete the sandbox you want to update and let the installer recreate it on the next apply run. The installer checks each sandbox’s state: a missing sandbox is created with the current policy, while a running sandbox is left in place.

    Deleting a sandbox also deletes its /sandbox volume, openshell-sandbox-<sandbox-id>-workspace, with all files in it. Copy out the files you want to keep before you delete the sandbox, as the row on a sandbox in Error in Troubleshooting describes. 
    openshell sandbox delete <sandbox-name> --workspace <workspace>

  4. Restart the VM so that saw-apply recreates the missing sandbox on boot:

    make openshell-saw-restart OPENSHELL_SAW_NAME=<name>

    With vm.liveInputs, saw-reconcile does not detect a governance-only change because the user’s own input hashes (installer, profiles, secrets) have not changed. A VM restart is still required.

Check: The new sandbox shows the updated policy fields in openshell sandbox get <name>.

Change a user’s BOM

A BOM change (new OpenShell version, different component digests) updates the installer ConfigMap.

With the default settings (vm.liveInputs: false), a change to the installer ConfigMap (which includes the BOM) or the cloud-init Secret updates a checksum annotation on the VM template. The running VM doesn’t pick up the new inputs until it restarts. The restart, which make openshell-saw-restart performs with virtctl restart, interrupts all running sandboxes for that user. Provider Secret changes are not checksummed: without vm.liveInputs, a Secret change is picked up only at the next boot; with vm.liveInputs, saw-reconcile detects it.

  1. Change the bom: block in the chart values to the new versions and digests. Tags are refused at render time and by the installer.

  2. Sync the chart (Argo CD sync, or helm upgrade on the manual path).

  3. Restart the VM so it picks up the new disks:

    make openshell-saw-restart OPENSHELL_SAW_NAME=<name>

  4. On boot, saw-install pulls only the changed components by digest, installs them, and restarts the gateway if a binary or its config changed. saw-apply then reconciles workspaces, providers, and sandboxes.

Check: make openshell-saw-status OPENSHELL_SAW_NAME=<name> shows the new component versions and ready: true.

Hot reconcile with vm.liveInputs

Experimental feature

Hot reconcile with vm.liveInputs is an experimental feature. It is part of SAW main at the baseline commit but is disabled by default, and its behavior may change.

Setting vm.liveInputs: true replaces the iso9660 disks with virtiofs mounts. Changes to the installer ConfigMap, profiles, and provider Secrets become visible inside the VM without a restart.

Turning the flag on requires recreating the VM because cloud-init writes the reconcile units only on first boot. Adding or removing an entry in additionalProviderSecrets also requires a restart even with live inputs, because it changes the VM template’s filesystems list.

When the guest detects a change, saw-reconcile runs:

  • A path unit (saw-inputs.path) watches /run/saw/installer, /run/saw/profiles, and /run/saw/secrets. A 60-second timer (saw-inputs.timer) is the fallback.

  • The reconcile script debounces for 10 seconds so that a single Helm upgrade that rewrites several files becomes one run.

  • If the installer tree changed (BOM or gateway config), reconcile runs install then apply. If only profiles or Secrets changed, it runs apply only.

  • On failure, the same input hash is not retried for 300 seconds (SAW_RECONCILE_BACKOFF). A new input change resets the backoff immediately.

  • All units serialize on /run/saw/lock, so reconcile never overlaps with the boot-time saw-install or saw-apply.

Check: make openshell-saw-status OPENSHELL_SAW_NAME=<name> shows inputs.upToDate: true after the reconcile finishes.

Signing modes

The signing-mode setting (signing.mode in the chart values) controls how the installer verifies component images and the installer bundle. Three modes are available:

off

No signature checks. The installer pulls and installs components without verification.

warn (default)

The installer checks signatures and logs a warning for unsigned or failed components. Installation proceeds regardless.

enforce

The installer refuses to install any component that fails its signature check. enforce also requires signing.trustKeys or a keyless identity to be configured.

The effective mode is the stricter of the chart value and a floor the golden image can pin at /etc/saw/signing-mode. This floor prevents a namespace editor from downgrading enforce to off by editing the installer ConfigMap.

Keyless signing (signing.identity and signing.issuer) is accepted as a valid BOM shape but always fails verification at the baseline. Podman’s policy.json cannot match a Fulcio identity by the https:// URI format that the BOM validation requires. A component configured with keyless signing behaves like one with no signer: warn records it unsigned, enforce fails it. Use signing.trustKeys with a keyRef until keyless support is available.

Pruning

When you remove an object from a SAW-BOM profile (a workspace, provider, or sandbox), the installer’s prune step decides what happens to the corresponding object in the gateway. The prune settings in the chart values control this behavior:

prune.mode
off

No pruning. Removed objects stay in the gateway.

report (default)

The installer logs what it would delete but removes nothing.

on

The installer deletes objects that no longer appear in the profile.

prune.sandboxes

Defaults to false. Even with prune.mode: on, sandboxes are kept unless this flag is true, because sandboxes hold user work.

Objects the installer never deletes, regardless of mode:

  • The default workspace.

  • Any workspace, sandbox, or provider created by hand. The installer prunes only objects recorded in its ledger, /var/lib/saw/user/managed.json. It also labels the workspaces and sandboxes it creates saw.redhat.com/managed=true, and prune keeps such an object when the label is missing.

The first successful apply adopts whatever already matches the current profiles and deletes nothing. Deletion order is: sandboxes, providers, provider profiles, then workspaces. A workspace is deleted only when it is empty afterwards.

Update the golden image

Every user VM clones its root disk from the golden image, the openshell-gateway VM image. make copy-images mirrors that image from QUAY_REPO (default quay.io/rh-ai-quickstart) into the internal registry in openshell-agents and tags it with OPENSHELL_VERSION and latest. On SAW main, OPENSHELL_VERSION still names a 0.0.x tag while the BOM installs OpenShell 0.1.2-rhaiv.0. That’s expected, because the tag names the golden image build, not the OpenShell release the VMs run. The in-guest installer always installs OpenShell from the BOM.

  1. Mirror the new image into the cluster’s internal registry:

    make copy-images

    To mirror a different tag, add OPENSHELL_VERSION=<tag>. If quay has no image with that tag, the target falls back to the v-prefixed tag and then to latest, and still stores the result under the tag you asked for. At this baseline the default tag takes that fallback, and the latest image on quay predates the installer bundle verifier verify-bundle.

    Check: oc get imagestream openshell-gateway -n openshell-agents lists the mirrored tag and latest.

  2. Make new VMs clone the mirrored image.

    Mirroring a new image alone changes no VM, existing or new. The golden DataVolume openshell-gateway-golden imports the latest tag only when it doesn’t exist yet, and each VM clones its root disk only once, when its <name>-root DataVolume is created. New VMs keep cloning the old golden disk too, because the openshell-gateway DataSource they clone from points at the openshell-gateway-golden PVC. To replace the golden disk, this step deletes three resources: the golden DataVolume openshell-gateway-golden, its PVC, and the openshell-gateway DataSource. make build-gateway-podman deletes the same three before a build, and also the earlier builds and the openshell-gateway ImageStream, which this step keeps.

    Run this step only while no VM is being created. A root-disk clone that is still running can keep the old PVC in Terminating. That VM then still gets the old image, and the next golden DataVolume, which has the same name, can stall until the old PVC is gone. Before you start, confirm with oc get datavolumes -A that every <name>-root DataVolume reports Succeeded. The deletion also leaves no golden disk until the next VM creation has imported the image again, and every VM created until the import finishes waits for it. Existing VMs keep their root disks and stay on the old image. 
    oc delete datavolume openshell-gateway-golden -n openshell-agents
oc delete pvc openshell-gateway-golden -n openshell-agents --ignore-not-found
oc delete datasource openshell-gateway -n openshell-agents

    The PVC belongs to the DataVolume and usually goes away with it, so --ignore-not-found keeps the second command from failing. The prepare Job of the next VM that SAW creates finds no golden DataVolume. It imports the latest tag again, recreates the DataSource, and then lets the VM clone its root disk from the new golden disk.

    Check: oc get datavolume openshell-gateway-golden -n openshell-agents reports Succeeded after the next VM creation.

Build the golden image from your checkout

Instead of mirroring, make build-gateway-podman builds the golden image from your SAW checkout in the cluster, so the image contains verify-bundle and cosign. That gets you the verifier, not a verified bundle. At this baseline the chart ships no signed bundle.sigstore.json, so the installer still records the bundle as unsigned. A signed bundle alone wouldn’t verify either, because the build adds no public key to /etc/saw/trust, and without a key the verifier records the bundle as failed. The note at the copy-images step of Install manually describes what bundle verification also needs.

The target first deletes the golden DataVolume openshell-gateway-golden, its PVC, the openshell-gateway DataSource, the earlier builds of the image, and the openshell-gateway ImageStream. It then recreates the ImageStream, the DataVolume, and the DataSource from the new build. The new ImageStream holds only the latest tag of the build, so the OPENSHELL_VERSION tag that make copy-images stored is gone. Existing VMs keep their root disks, and VMs created afterwards clone the new golden disk. After the build, the target pushes the image to QUAY_REPO as latest and as the OPENSHELL_VERSION tag. The default QUAY_REPO is quay.io/rh-ai-quickstart. Without push rights to that organization, the push fails after the build, and with them it replaces the published latest image.

Log in to a registry where you can push images, then run the build with QUAY_REPO set to your organization there:

podman login quay.io
make build-gateway-podman QUAY_REPO=quay.io/<your-org>

Check: oc get datavolume openshell-gateway-golden -n openshell-agents reports Succeeded once the new image is imported.

Upgrade OpenShell

Everything that talks to a gateway must come from the same OpenShell release series: the BOM each VM installs, the shared governance interceptor, and every user’s CLI. SAW is stricter: all four BOM components and the interceptor must come from one exact release. An upgrade therefore moves all three together. A move to a new release series also recreates the gateway state on every VM, so plan it as a maintenance window.

A new release series recreates every sandbox

The installer compares the old and new gateway versions on major.minor, so going from 0.0.x to 0.1.x counts as a move to a new release series. On that move, each VM stops the gateway, removes every OpenShell sandbox container, and moves the gateway database aside to gateway.<old version>.<epoch>. The apply step then recreates workspaces, providers, and sandboxes from the SAW-BOM. Sandboxes and providers that users created themselves don’t come back, because they live in the moved database and apply recreates only the objects in the user’s BOM profiles. Workspace memberships that you added by hand with openshell workspace member add don’t carry over, because they live in the moved database and the installer adds back only the ownerSubject membership (see When to set ownerSubject). The gateway’s TLS material is kept.

Data in /sandbox doesn’t carry over. Each sandbox’s /sandbox is the Podman volume openshell-sandbox-<sandbox-id>-workspace, and the recreated sandboxes get new IDs and new, empty volumes. The installer keeps the old volumes and lists them in the installer log, so you can copy data over by hand.

  1. Update the bom: block in the chart values (charts/openshell-saw/values.yaml) to the new release. Take all four components (cli, gateway, supervisor, and the sandbox runtime image) from the same release, and pin each image by digest. The installer refuses a BOM whose components carry different versions.

  2. Build or pick the governance interceptor image for the same tag. Set source.git.ref in image-builder-charts/helm/governance-interceptor-image/values.yaml to the new OpenShell tag. On a push to main, a GitHub workflow builds the interceptor from that tag and publishes it as ghcr.io/<owner>/governance-interceptor:<tag>. To build it into the cluster’s internal registry instead, run make build-governance-interceptor-local OPENSHELL_INTERCEPTOR_REF=<tag>. Then set image in charts/governance-interceptor/values.yaml to the new image.

    A gateway that fails the version check doesn’t start. On the move from 0.0.x, the check fails whenever the gateway and the interceptor come from different series, so update the interceptor and restart every VM in the same window.

  3. Sync the charts and restart the VMs as in Change a user’s BOM. On the first boot with the new BOM, the installer log reports the release-series move and lists the kept /sandbox volumes.

  4. Tell users to install the CLI from the new release before they use the gateway again (see Install the OpenShell CLI). OpenShell does not support a 0.0.x CLI with a 0.1.x gateway.

Check: The installer logs (serial console or make openshell-saw-logs) show the new component versions being installed, and openshell status from a user’s CLI reports the new gateway version.

Remove a user

To remove a user, delete their entry from overrides/saw-users.yaml and sync. The pruneOnRemove flag in charts/saw-users/values.yaml controls whether the VM is also deleted:

pruneOnRemove: false (default)

Argo CD deletes the user’s Applications but leaves the namespace and VM in place. The namespace is marked Prune=false so the parent app does not delete it.

pruneOnRemove: true

The Applications get a foreground finalizer and the openshell-saw chart keeps its pre-delete hook, so Argo CD deletes the VM and the namespace follows.

You can set pruneOnRemove on a single user entry in overrides/saw-users.yaml before removing them, instead of changing the global default.

For the quickstart path, delete a single user’s resources directly:

make openshell-saw-delete OPENSHELL_SAW_NAME=<name>

This runs helm uninstall in the user’s namespace and deletes the namespace if it carries the openshell.pattern/saw=true label.

Check: oc get ns saw-<name> returns "not found" after the namespace is cleaned up.

Uninstall

Three levels of cleanup are available, from targeted to complete.

Delete a single user’s VM and namespace
make openshell-saw-delete OPENSHELL_SAW_NAME=<name>
Delete shared infrastructure (Keycloak, image streams, golden image) without touching the pattern
make delete-all

Sandbox releases must still be uninstalled individually.

Full pattern uninstall
make uninstall

This deletes all VMs and DataVolumes, removes the HyperConverged CR, removes the Argo CD Applications through the validated patterns framework, and cleans up OLM state for OpenShift Virtualization.

Check: oc get patterns secure-agent-workspace -n patterns-operator returns "not found" after a full uninstall.
