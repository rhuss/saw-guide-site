Onboard users

Once the platform is installed, the next step is to add users. This page walks you through creating a Keycloak account, adding the user to the SAW configuration, choosing a BOM profile, and collecting the items you hand over so the user can connect.

Figure 1. The onboarding workflow from the SAW admin’s perspective (left) to what the SAW user receives (right).

Naming rules

Every user name must follow three rules, enforced by the saw-users chart at render time:

Lowercase DNS label

Only lowercase letters, digits, and hyphens. The name must start and end with a letter or digit.

At most 19 characters

OpenShell limits VM names to 19 characters. The chart rejects anything longer.

Unique

No two users may share the same name. The chart fails the Helm render if it finds a duplicate.

The name becomes the VirtualMachine name, the Namespace name (saw-<name>), and part of every Route hostname. Pick something short and recognizable.

Create a Keycloak user

Before you add a user to the SAW configuration, create a Keycloak account for them in the openshell realm. You can do this through the Keycloak admin console or through the Keycloak Admin API.

Assign the user the openshell-user realm role. This role grants access to the OpenShell gateway, but only within workspaces where the user has membership.

Grant the openshell-admin role only if the user needs to administer the gateway itself (for example, creating workspaces or managing other users outside the managed SAW lifecycle). Most users should stay with openshell-user.

Note the new user’s ID. OpenShell identifies a user by the sub claim of their token, which openshell whoami prints as the subject. Keycloak sets sub to the user’s ID unless a protocol mapper overrides it, and the openshell realm that SAW imports has no such mapper. The admin console shows the ID on the user’s Details tab, and the Admin API returns it as the user’s id. You can therefore read the subject as soon as the account exists and use it as ownerSubject (see When to set ownerSubject).

Remove or change the default test users before onboarding real people

The openshell-keycloak chart ships with test defaults that are not safe for production.

Test users with passwords equal to their names

The testUsers list in charts/openshell-keycloak/values.yaml creates four users: developer/developer, admin/admin, alice/alice, and bob/bob. Remove these test users or change their passwords through the Keycloak admin console before you expose the cluster.

Self-registration enabled

registrationAllowed: true lets anyone with access to the Keycloak login page create their own account. Set keycloak.registrationAllowed to false in charts/openshell-keycloak/values.yaml before you expose the cluster.

Store per-user secrets in Vault

By default every user’s workspace reads secrets from the shared hub prefix (secret/data/hub). If a user needs their own inference key or a different model, create a per-user Vault prefix.

Edit ~/values-secret.yaml and add a vaultPrefixes entry under the inference group. The path is relative to secret/data, for example hub/saw-jane:

  - name: inference
    vaultPrefixes:
      - hub/saw-jane
    fields:
    - name: provider
      value: build
    - name: model
      value: nvidia/nemotron-3-super-120b-a12b
    - name: api_key
      path: ~/.nvidia-api-key-jane

Then set that user’s vaultPrefix in the user list (next step) to secret/data/hub/saw-jane. The saw-users chart doesn’t create Vault entries on its own. You load them through the validated patterns secret mechanism or with the vault CLI.

Add the user and choose profiles

  • GitOps

  • Manual

Edit overrides/saw-users.yaml and add an entry for each new user. Every entry needs a name and a list of profiles.

# https://github.com/validatedpatterns-sandbox/secure-agent-workspace/blob/4768f02d4415449de74403df62bad0c03630448e/overrides/saw-users.yaml
users:
  - name: jane                  (1)
    profiles:                   (2)
      - data-science
    ownerSubject: "<keycloak-user-id>"                    (3)
    vaultPrefix: secret/data/hub/saw-jane                 (4)
  - name: dev-team-gpu          (5)
    profiles:
      - data-science
      - custom-inference
1 Lowercase DNS label, at most 19 characters.
2 One or more BOM profile names. The default is data-science.
3 The user’s subject, which is their Keycloak user ID (see Create a Keycloak user). Without a workspace membership, the user can’t work on their gateway (see When to set ownerSubject). When set, the installer calls openshell workspace member add --subject <ownerSubject> --role admin for each workspace, making that user a workspace admin. Copy the ID from Keycloak when you create the account and set it in the same commit as the new entry. If you don’t have the ID yet, add it later as described in Set ownerSubject for an existing user.
4 Optional per-user Vault prefix. Without it, the user reads the shared secret/data/hub prefix.
5 A second user without ownerSubject or a custom vaultPrefix. This user gets the chart defaults and no workspace membership until you add one.

Commit and push your changes. Argo CD picks up the new entries, creates one Namespace (saw-<name>) and three Application objects per user (saw-<name>-secrets, saw-<name>-bom, saw-<name>), and the VM boots.

Check: Confirm the new user’s VirtualMachine exists.

oc get vm -A -l openshell.pattern/owner

Run make openshell-saw-create for each new user. The target creates the Namespace, deploys the SAW-BOM profiles, creates provider credential Secrets, and deploys the VM.

When you onboard someone else, set OWNER to the user’s name and OWNER_SUBJECT to their Keycloak user ID (see Create a Keycloak user). The installer then makes that subject an admin of the user’s workspaces. OWNER without OWNER_SUBJECT sets the owner name but no subject, so the installer adds no workspace member. With OWNER set, the target doesn’t prompt, so the command also runs from a script. The command reads the provider keys from files, as described in the "Create the user VM" step of Install manually. The default data-science profile also needs the Brave Search key in WEB_SEARCH_API_KEY. Before you run the target, export KEYCLOAK_NS as in step 3 of Install manually, because the target looks up the OIDC issuer in that namespace. When KEYCLOAK_NS doesn’t name the namespace of your Keycloak, the target finds no issuer and deploys the gateway without OIDC, and it reports no error.

WEB_SEARCH_API_KEY="$(cat ~/.brave-api-key)" \
make openshell-saw-create \
  OPENSHELL_SAW_NAME=jane \
  OWNER=jane \
  OWNER_SUBJECT=<keycloak-user-id> \
  PROVIDER=build \
  MODEL=nvidia/nemotron-3-super-120b-a12b \
  API_KEY="$(cat ~/.nvidia-api-key)"

Without OWNER, the target reads your own identity from the token that make login saved and asks who owns the VM:

Press Enter to set owner to '<you>', or type a different owner:

In that case the target takes the subject from your own token and ignores OWNER_SUBJECT, even when you type a different owner name. The installer then makes you, not the user, the workspace admin, so leave OWNER unset only for a VM that you work in yourself.

Check: Confirm the VirtualMachine exists and is running.

oc get vm -n saw-jane

Understand BOM profiles

Each profile bundles workspaces, providers, and sandboxes into a ready-to-apply configuration. The SAW repository ships two profiles:

data-science (default)

Two workspaces (default and cuda-dev), an NVIDIA Build provider, a Brave Search provider, and five sandbox definitions across both workspaces (two enabled by default). The Brave Search provider exists in the default workspace, but no sandbox in the profile attaches it. Every sandbox lists only the NVIDIA provider, so the agents in the default sandboxes have no web search.

custom-inference

One workspace with an OpenAI-compatible provider that reads its base URL, model, and key from the inference Secret. Use this profile when you run a self-hosted model server (for example vLLM or Ollama).

Profiles live under charts/saw-bom/profiles/<profile-name>/<workspace-name>/. Each workspace directory contains three files: workspace.yaml, providers.yaml, and sandbox.yaml.

The sandbox.yaml from the data-science profile shows how sandbox entries are structured:

# Excerpt from https://github.com/validatedpatterns-sandbox/secure-agent-workspace/blob/4768f02d4415449de74403df62bad0c03630448e/charts/saw-bom/profiles/data-science/default/sandbox.yaml
apiVersion: saw.redhat.com/v1alpha1
kind: Sandboxes
metadata: {}
spec:
  sandboxes:
    - name: notebook             (1)
      type: openclaw             (2)
      enabled: true              (3)
      image: quay.io/rh-ai-quickstart/openclaw-openshell:latest (4)
      providers:                 (5)
        - nvidia
    - name: cuda-sandbox
      type: nemoclaw
      enabled: false
      agent: openclaw
      image: quay.io/rh-ai-quickstart/nemoclaw-sandbox:latest
      providers:
        - nvidia
1 Sandbox name, also a DNS label, at most 19 characters.
2 Sandbox type: openclaw, nemoclaw, or generic. The type determines which agent harness runs inside the sandbox. At this baseline a nemoclaw sandbox falls back to plain OpenClaw (see the note in Work with sandboxes).
3 Set enabled: false to include the definition without creating the sandbox on boot.
4 The container image pulled into the sandbox.
5 Which providers this sandbox can reach. Each name must match a provider in providers.yaml.

Every provider’s type field must match a governance profile ID. See How governance works for the full list of allowed provider types and how the interceptor validates them.

When to set ownerSubject

A user needs workspace membership to work on their gateway. In SAW, only the ownerSubject setting creates one.

The subject is the Keycloak user ID, which you find on the user’s Details tab in the admin console (see Create a Keycloak user). openshell whoami shows the same value under Subject once the user has logged in.

When you set ownerSubject to that ID, the in-VM installer calls openshell workspace member add --subject <ownerSubject> --role admin for each workspace in the user’s BOM profiles. This makes the user a workspace admin. They can list, connect to, and create sandboxes, and they can create providers whose type matches a governance profile. The installer adds the membership each time it applies the BOM, so it comes back after a release-series upgrade recreates the gateway state.

Without ownerSubject, the user’s workspaces have no members, because neither the gateway nor the installer adds users on its own. The user can log in and run openshell whoami, but the gateway rejects their sandbox and provider requests. They can’t list, connect to, or create sandboxes from the CLI. They also can’t read the OpenClaw UI token, because reading it takes openshell sandbox exec.

Set ownerSubject for every user who works in their own VM. Because the subject is the user ID, you can set it when you add the user, before their first login, and the user can work as soon as the installer finishes. For a VM that already runs without it, see Set ownerSubject for an existing user. If you want a user to run sandboxes without managing providers, leave ownerSubject empty and add a user membership yourself. Register the user’s gateway with make openshell-saw-configure-gateway OPENSHELL_SAW_NAME=<name> and sign in with an account that has the openshell-admin role. Then run this command once for each workspace in the user’s profiles, replacing <workspace> with the workspace name. The default data-science profile has two workspaces, default and cuda-dev.

openshell workspace member add --workspace <workspace> --subject <subject> --role user

Check: List the members of each workspace and confirm that the user’s subject appears with the role user.

openshell workspace member list --workspace <workspace>

A workspace user can create, use, and delete sandboxes and use the providers you configured, but can’t create or change providers. Only an account with the openshell-admin role can assign the workspace admin role. The installer doesn’t restore memberships that you add by hand, so add them again after a release-series upgrade.

What to hand the user

After the VM is running and the installer finishes, collect these items and give them to the user. The first five items let the user connect with the OpenShell CLI. The last two cover the web UIs.

Item What it is How the admin obtains it

Keycloak username and password

The credentials you created in the Keycloak admin console.

You set these when creating the user account.

OIDC issuer URL

The Keycloak realm URL, format https://<keycloak-host>/realms/openshell.

Run make keycloak-issuer KEYCLOAK_NS=<keycloak-namespace>. KEYCLOAK_NS names the namespace of your Keycloak and defaults to saw-keycloak.

OIDC client ID

Defaults to openshell-cli.

A known constant. Provide it as-is unless you changed the client ID.

Gateway route URL

The HTTPS URL of the user’s gateway Route.

oc get route <name>-gateway -n saw-<name> -o jsonpath='https://{.spec.host}'

Gateway CA certificate

The self-signed CA the gateway uses for mTLS. The user’s CLI needs it to verify the gateway’s TLS certificate.

Extracted from the sandbox VM over SSH. Run make openshell-saw-configure-gateway OPENSHELL_SAW_NAME=<name> (which calls scripts/extract-gateway-ca.sh internally) and copy the resulting ca.crt file from ~/.config/openshell/gateways/<name>/mtls/ca.crt.

OpenClaw UI access

How the user opens the OpenClaw web UI in their sandboxes. SAW creates a Route named dashboard for this UI, which targets port 18789 of the user’s VM. At this baseline OpenClaw listens inside the sandbox container, which has no network of its own, so the Route does not reach the OpenClaw UI.

Don’t hand over the Route URL. Point the user to Open the OpenClaw web UI, which opens the UI through a port forward.

OpenShell Dashboard URL

The HTTPS URL of the Route named webui, which leads to the OpenShell Dashboard through oauth2-proxy and a Keycloak login.

oc get route <name>-webui -n saw-<name> -o jsonpath='https://{.spec.host}'

Check: Verify that the gateway responds before handing over the URL. The make openshell-saw-configure-gateway run from the CA certificate row has registered the gateway in your own CLI and signed you in through the browser. If you have not run it yet, run it first. Then query the gateway’s status:

openshell --gateway <name> status

The output shows Status: Connected, the authentication state, and the gateway version. Don’t check with curl on /health through the gateway Route. The gateway serves its health endpoints only on a separate health listener, which is off by default, and not on the port behind the Route.

The user guide (starting at Access your workspace) walks users through connecting with these items.

Set ownerSubject for an existing user

Use these steps when a user’s VM already runs without ownerSubject, for example because you didn’t have the user’s ID when you added them. Until you set it, their workspaces have no members, and the user can’t list, connect to, or create sandboxes. Read the ID from the user’s Details tab in the Keycloak admin console. Without access to the admin console, ask the user to log in and send you the Subject that openshell whoami shows.

  1. Set the subject as the user’s ownerSubject. On the GitOps path, add it to the user’s entry in overrides/saw-users.yaml, then commit, push, and let Argo CD sync:

    users:
  - name: jane
    profiles:
      - data-science
    ownerSubject: "<keycloak-user-id>"

    On the manual path, export KEYCLOAK_NS as in step 3 of Install manually, then run make openshell-saw-create again with the same variables as before, plus OWNER=<name> and OWNER_SUBJECT=<keycloak-user-id>. The target runs helm upgrade --install, so it updates the existing release. It replaces the release’s values with the ones from this run, so a run that finds no Keycloak in KEYCLOAK_NS turns the gateway into one without OIDC.

  2. Restart the VM so that the installer reads the new value:

    make openshell-saw-restart OPENSHELL_SAW_NAME=<name>

    ownerSubject is part of the installer ConfigMap. The change updates the VM’s installer inputs, but the running VM doesn’t pick them up until it restarts (see Change a user’s BOM). With vm.liveInputs turned on, skip the restart, because saw-reconcile detects the changed ConfigMap and runs install and apply.

Check: List the members of each workspace and confirm that the user’s subject appears with the role admin.

openshell workspace member list --workspace <workspace>
