Install manually

Baseline

This guide describes SAW at commit 4768f02 (2026-10-02), which deploys OpenShell 0.1.2-rhaiv.0. Later SAW commits may rename targets or change defaults.

The manual path deploys SAW one component at a time through make targets, with no Argo CD or Git round trips required. It is the fastest way to test changes, iterate on a development cluster, or bring up a single sandbox for evaluation. The root Makefile includes Makefile-quickstart, so every target documented on this page runs as make <target> from the repository root.

Before you begin, confirm that every item on the Prerequisites and sizing page is in place. You need cluster-admin access, the CLI tools listed there, and enough capacity for at least one user VM plus the shared-services overhead.

Steps

  1. Clone the repository and check out the baseline commit.

    Clone the SAW repository and switch to the commit this guide is written against. Every command on this page then matches the code you run.

    git clone https://github.com/validatedpatterns-sandbox/secure-agent-workspace.git
cd secure-agent-workspace
    git checkout 4768f02d4415449de74403df62bad0c03630448e

  2. Log in to OpenShift with cluster-admin.

    The manual targets create Namespaces, operator subscriptions, and cluster-scoped resources, all of which require cluster-admin privileges.

    oc login --server=https://api.<cluster>:6443 -u <user>

    If the API server presents a self-signed certificate, oc login reports a certificate signed by an unknown authority. Pass the cluster’s CA certificate with --certificate-authority=<ca-file> so that oc trusts it. On a disposable lab cluster, you can skip the check with --insecure-skip-tls-verify=true instead. Do not skip it on any other cluster. Without the check, others could intercept any data you send to the server, as the oc documentation warns.

    Check: Confirm that you are logged in and that whoami returns a cluster-admin user.

    oc whoami

  3. Set the variables for the following steps.

    Several targets on this page read the Keycloak namespace and the VM name from your shell environment. Export both now, in the terminal where you run the remaining steps.

    export KEYCLOAK_NS=saw-keycloak
export OPENSHELL_SAW_NAME=alice

    An exported variable reaches only the commands that you start from the shell that exported it. A new terminal starts a new shell, so export both variables again there, for example in the second terminal that follows the installer in step 11.

    KEYCLOAK_NS

    The namespace of the RHBK operator and of Keycloak. Keep the default saw-keycloak unless your cluster already runs RHBK in another namespace. In that case, export that namespace instead, as described in If your cluster already runs RHBK. If you subscribed a second RHBK operator in saw-keycloak, as the caution in that section allows, keep saw-keycloak. The check-prereqs (step 4), keycloak (step 7), keycloak-check and keycloak-issuer (step 8), login (step 10), openshell-saw-create (step 11), and openshell-saw-configure-gateway (step 12) targets read it. When it is unset, they fall back to saw-keycloak.

    OPENSHELL_SAW_NAME

    The name of the user VM. It also names the VM’s namespace (saw-<name>) and the gateway entry in your openshell CLI configuration. It must have 19 characters or fewer; step 11 lists all naming rules. The openshell-saw-create, openshell-saw-logs, and openshell-saw-status (step 11), openshell-saw-configure-gateway (step 12), and openshell-saw-restart targets read it. So do the targets in Governance profiles. Without it, those openshell-saw-* targets stop with Error: OPENSHELL_SAW_NAME is required.

  4. Verify prerequisites.

    make check-prereqs checks that OpenShift Virtualization and Red Hat build of Keycloak operators are installed and that the required CLI tools (oc, helm, openssl) are available. It looks for the RHBK operator in KEYCLOAK_NS. It also reports whether virtctl and openshell are present (warnings, not hard errors at this stage).

    This target changes the cluster when the internal image registry has no default-route Route. It then enables the route by setting defaultRoute to true in the cluster’s image registry configuration. The copy-images target in step 6 sets the same field.

    		 
    make check-prereqs

    If the RHBK operator runs only in a namespace other than KEYCLOAK_NS, the target stops with Error: RHBK operator found in namespace '<namespace>', but KEYCLOAK_NS is 'saw-keycloak'. Export the namespace from that message as KEYCLOAK_NS, as described in step 3, and run the target again.

    Check: The output ends with Prerequisites OK.

  5. Generate SSH keys.

    make generate-keys creates an Ed25519 keypair at ~/.generated-ssh-keys/sandbox-ssh. SAW injects the public key into every user VM so that virtctl ssh works without a password.

    make generate-keys

    Check: Confirm that the keypair exists.

    ls -l ~/.generated-ssh-keys/sandbox-ssh*

  6. Copy pre-built images to the cluster.

    The golden VM image that every user VM clones its root disk from is hosted on quay.io/rh-ai-quickstart. make copy-images mirrors it into the cluster’s internal registry so that DataVolumes can reference it locally. On macOS, the target runs in-cluster skopeo Jobs to avoid upload issues with podman-machine. The target asks quay for the tag in OPENSHELL_VERSION, then for the same tag with a v prefix, and otherwise falls back to latest. It stores the image it finds under the OPENSHELL_VERSION tag and also tags that image latest. On SAW main, OPENSHELL_VERSION is still a 0.0.x tag. That tag names the golden image build, while the VM installs OpenShell 0.1.2-rhaiv.0 from its BOM.

    make copy-images

    Check: Confirm the ImageStream exists in the openshell-agents namespace.

    oc get imagestream -n openshell-agents
    The mirrored image has no bundle verifier

    At this baseline, quay has no golden image under that 0.0.x tag or its v-prefixed form, so make copy-images mirrors latest. That image was built before SAW added the installer bundle verifier, verify-bundle. On boot, saw-stage-installer logs verify-bundle is not in this golden image; staging without verification. In the default warn signing mode the VM installs anyway, and in enforce mode the install stops. In warn mode, make openshell-saw-status also lists each OpenShell component as unsigned, whichever golden image the VM runs, because the baseline BOM gives no component a signature.
    Building the golden image deletes the current one

    To get the bundle verifier, build the golden image from the baseline with make build-gateway-podman instead of running make copy-images. The target first deletes the golden DataVolume openshell-gateway-golden, its PVC, the openshell-gateway DataSource, the earlier builds of the image, and the openshell-gateway ImageStream. It then builds the image in the cluster, creates the golden DataVolume and DataSource from it, and pushes the image to QUAY_REPO as latest and as the OPENSHELL_VERSION tag. The default QUAY_REPO is quay.io/rh-ai-quickstart, so log in to a registry where you can push images and set QUAY_REPO to your organization there:

    podman login quay.io
make build-gateway-podman QUAY_REPO=quay.io/<your-org>

    Even a golden image built this way records the bundle as unsigned at this baseline, because the chart ships no signed bundle.sigstore.json. Verification also needs your public key in /etc/saw/trust, which the image build does not add.

  7. Deploy Keycloak.

    make keycloak deploys a Keycloak instance with its PostgreSQL database in KEYCLOAK_NS and imports the OpenShell realm through the RHBK operator. The RHBK operator must already be installed in that namespace.

    make keycloak

    If you exported the namespace of an existing RHBK in step 3, what the target does depends on the Keycloak instances in that namespace, as If your cluster already runs RHBK describes. When another Keycloak runs there but SAW’s openshell-keycloak does not, and that Keycloak is not yet configured for OpenShell, run the target with USE_EXISTING_KEYCLOAK=yes instead:

    make keycloak USE_EXISTING_KEYCLOAK=yes

    The target then imports only the openshell realm into that Keycloak and deploys no second Keycloak and no database. Without the variable, it asks before it imports the realm, and it stops with an error when it runs without a terminal. If that Keycloak already has an openshell realm that fails the check, the target imports nothing and stops with Error: realm 'openshell' already exists on '<keycloak>' but is not configured for OpenShell.

    Check: Confirm that Keycloak is running and the realm import succeeded.

    oc get keycloak -n "$KEYCLOAK_NS"
oc get keycloakrealmimport -n "$KEYCLOAK_NS"

  8. Verify Keycloak configuration.

    make keycloak-check verifies that the realm, the openshell-cli client, and the required roles (openshell-admin, openshell-user) exist and are correctly configured. make keycloak-issuer prints the OIDC issuer URL that subsequent steps use. Both targets look for Keycloak in the KEYCLOAK_NS that you exported in step 3.

    make keycloak-check
make keycloak-issuer

    Check: keycloak-check reports all checks as passed and keycloak-issuer prints a URL ending in /realms/openshell.

  9. Deploy the governance interceptor.

    The governance interceptor validates every sandbox operation against an admin-defined policy. Deploy the policy ConfigMap first, then the interceptor itself. Both charts install into the shared openshell-agents namespace. The governance-interceptor chart pulls ghcr.io/validatedpatterns-sandbox/governance-interceptor:v0.1.2, built from the same OpenShell release as the gateways (see Interceptor and gateway versions). To build the interceptor in the cluster instead, run make build-governance-interceptor-local and set the chart’s image to that build. OPENSHELL_INTERCEPTOR_REF (default v0.1.2) selects the OpenShell tag that the target builds from.

    helm upgrade --install governance-policy charts/governance-policy \
  --namespace openshell-agents
helm upgrade --install governance-interceptor charts/governance-interceptor \
  --namespace openshell-agents

    Check: Confirm both Helm releases are deployed.

    helm list -n openshell-agents

  10. Authenticate with the OIDC provider.

    make login opens a browser window pointing at the Keycloak login page. Sign in with one of the test users (for example alice / alice) or a user you created in the Keycloak admin console. The target stores a token under ~/.config/openshell/oidc/.

    make login

    Check: Confirm your identity.

    make whoami

  11. Create the user VM.

    make openshell-saw-create provisions a gateway VirtualMachine, deploys the SAW-BOM profiles, creates the provider credential Secrets, and registers the OIDC configuration. Each user VM lives in its own Namespace (saw-<name>).

    The target requires these variables:

    OPENSHELL_SAW_NAME

    The name of the user VM, which you exported in step 3. Must be 19 characters or fewer, lowercase, and a valid DNS label. The script rejects longer names with a clear error.

    PROVIDER

    Inference provider key (for example gemini, anthropic, openai, build, openrouter, ollama).

    MODEL

    Model identifier for the provider.

    API_KEY

    API key for the inference provider.

    WEB_SEARCH_API_KEY

    Brave Search API key for the brave provider of the bundled profiles. The script reads it from the environment, so set it in front of make as in the example below.

    Optional variables:

    PROFILES

    Comma-separated SAW-BOM profiles (default: data-science). Use custom-inference with PROVIDER=openai and ENDPOINT_URL for a self-hosted model server.

    ENDPOINT_URL

    Base URL for a custom OpenAI-compatible endpoint (for example http://vllm.<namespace>.svc:8000/v1).

    CONTAINER_RUNTIME

    podman (default) or docker, controls the container runtime inside the gateway VM.

    The example uses the provider build, which serves NVIDIA models from build.nvidia.com. Sign in there and generate an API key, which starts with nvapi-. Save the key with a text editor in ~/.nvidia-api-key and make the file readable only for you:

    chmod 600 ~/.nvidia-api-key

    The command below reads the key from that file with API_KEY="$(cat ~/.nvidia-api-key)", so your shell history records the command but not the key.

    Both bundled SAW-BOM profiles, data-science and custom-inference, also create a brave provider in the default workspace. Its credential comes from a Secret named web-search, which the target creates only when the environment variable WEB_SEARCH_API_KEY holds a key. WEB_SEARCH is a different variable and does not create the Secret. Without the key, the apply stage in the VM stops with credential for provider 'brave' in workspace 'default' not found. Get a key from the Brave Search API dashboard and save it in ~/.brave-api-key the same way. No sandbox in either profile attaches the brave provider, so the key satisfies the installer but gives the default agent no web search (see Work with sandboxes).

    WEB_SEARCH_API_KEY="$(cat ~/.brave-api-key)" \
make openshell-saw-create \
  PROVIDER=build \
  MODEL=nvidia/nemotron-3-super-120b-a12b \
  API_KEY="$(cat ~/.nvidia-api-key)"

    The target reads your identity from the token that make login saved in step 10 and asks who owns the VM:

    Press Enter to set owner to 'alice', or type a different owner:

    Press Enter to make yourself the owner. Unless you set OWNER, the target also takes the subject from your token, and the installer makes that subject an admin of the VM’s workspaces. The target waits for this answer, so a script has to supply it. Pipe in an empty line, which keeps the subject detection:

    printf '\n' | WEB_SEARCH_API_KEY="$(cat ~/.brave-api-key)" \
make openshell-saw-create \
  PROVIDER=build \
  MODEL=nvidia/nemotron-3-super-120b-a12b \
  API_KEY="$(cat ~/.nvidia-api-key)"

    Setting OWNER=<name> instead skips both the prompt and the subject detection, so the installer adds no workspace member unless you also set OWNER_SUBJECT (see When to set ownerSubject).

    When KEYCLOAK_NS does not name the namespace of your Keycloak, the target finds no OIDC issuer and deploys the gateway without OIDC. If that namespace has a Route, the target instead builds a wrong issuer URL from the Route’s host. It reports no error in either case. This happens, for example, in a new terminal where you set OPENSHELL_SAW_NAME again, by export or as a make argument, but not KEYCLOAK_NS, while your Keycloak runs outside saw-keycloak. Check the issuer that the Helm release received:

    helm get values "$OPENSHELL_SAW_NAME" -n "saw-$OPENSHELL_SAW_NAME" -o json | jq -r .oidc.issuerUrl

    Compare the output with the URL that make keycloak-issuer printed in step 8. A URL that ends in /realms/openshell alone doesn’t prove that it is right, because the wrong issuer ends the same way. If the command prints null or a different URL, export the right KEYCLOAK_NS and run make openshell-saw-create again with the same variables. Then restart the VM with make openshell-saw-restart, because the issuer is part of the installer ConfigMap.

    When the target finishes, its summary lists the <name>-dashboard Route as Dashboard: and suggests openshell gateway login as a next step. Skip both: step 12 signs you in without a separate login, and What to hand the user explains why you don’t hand over that Route.

    You can monitor the in-VM installer in another terminal with make openshell-saw-logs.

    Check: Confirm the VirtualMachine exists and is running.

    oc get vm -n "saw-$OPENSHELL_SAW_NAME"
make openshell-saw-status

    make openshell-saw-status is not read-only. Before it reads the installer status over SSH, it adds your public key ~/.generated-ssh-keys/sandbox-ssh.pub to the VM’s <name>-ssh-pubkey Secret, unless the Secret already holds that key. It then waits until the guest agent has written the key into the VM.

    Wait until openshell-saw-status shows "phase": "Done" for both the install and apply stages.

  12. Configure the gateway.

    make openshell-saw-configure-gateway extracts the gateway CA certificate from the user VM over SSH, registers the gateway in your local openshell CLI configuration, and selects it as the active gateway. This step requires admin access because it uses virtctl to SSH into the VM. When the target finds your Keycloak in KEYCLOAK_NS, it registers the gateway with OIDC, and openshell gateway add opens a browser window for the Keycloak sign-in.

    make openshell-saw-configure-gateway

    After you sign in in the browser, the output reports Authenticated successfully, and the CLI keeps the gateway’s token. You don’t need a separate openshell gateway login. If the browser sign-in fails, openshell gateway add removes the registration again and the target stops, so run the target again. On a machine without a browser, set OPENSHELL_NO_BROWSER=1 before you run the target. The CLI then uses the device code flow instead and reports Authenticated via device code after you approve the sign-in. When that sign-in does not finish, the registration stays without a token, and the target still reports the gateway as configured. In that case, and later whenever the gateway’s token has expired (see Token lifetime), sign in without registering the gateway anew:

    openshell gateway login "$OPENSHELL_SAW_NAME"

    Check: Confirm that sandboxes are visible through the gateway.

    openshell sandbox list
openshell sandbox list --workspace cuda-dev

Governance profiles

The SAW-BOM profiles bundled with the data-science profile include providers for NVIDIA Build and Brave Search. You can list, add, or remove governance provider profiles after the user VM is running. The profiles live in the shared governance-policy chart, so adding or removing one changes the profiles of every user VM. OPENSHELL_SAW_NAME only selects the gateway that the targets query, so pass the name of a user VM, or rely on the variable you exported in step 3:

make governance-list-profiles OPENSHELL_SAW_NAME=<name>
make governance-add-profile OPENSHELL_SAW_NAME=<name> PROFILE_NAME=github
make governance-remove-profile OPENSHELL_SAW_NAME=<name> PROFILE_NAME=github

Without the VM name, the targets fall back to the gateway name openshell-saw from the earlier single-user layout. If your openshell CLI configuration still has a gateway with that name, the targets act on it silently, whichever cluster it points to.

governance-add-profile and governance-remove-profile are written for the GitOps path. They change charts/governance-policy/profiles/ in your clone, commit the change, run git push origin HEAD, and then set the hard-refresh annotation on the Argo CD application governance-policy. After that, they query the gateway every 5 seconds, for up to 3 minutes, until the profile appears or disappears there. On the manual path, the target stops with an error after it has committed the change in your clone. With the detached HEAD from step 1, the push fails. On a branch that you can push, the commit reaches your remote, and the Argo CD refresh fails instead. To change the profiles on the manual path, edit the files in charts/governance-policy/profiles/ and run the helm upgrade --install governance-policy command from step 9 again.

The interceptor reads the profiles from its mounted ConfigMap. Kubelet propagates a changed ConfigMap into the interceptor Pod, typically within about 60 seconds, and the interceptor picks up the changed files on the next evaluation, without a VM restart. The gateways don’t cache profiles, because they ask the interceptor for them on each provider lookup (see Provider profiles follow the ConfigMap). A restart with make openshell-saw-restart adds nothing here and interrupts the user’s running sandboxes.

Token lifetime

The openshell-cli client in the Keycloak realm requests an access token lifespan of 86400 seconds (24 hours). Keycloak never issues an access token that outlives the user’s SSO session, though. The realm import sets no session timeouts, so Keycloak’s defaults apply: an SSO Session Max of 10 hours and an SSO Session Idle of 30 minutes. An access token is therefore valid for at most 10 hours after you sign in. The refresh token expires after 30 minutes without use.

make login and the gateway keep separate tokens. make login stores its token under ~/.config/openshell/oidc/, where make whoami and openshell-saw-create read it. openshell gateway add in step 12 stores the gateway’s own token, which the openshell CLI sends to the gateway. When the gateway’s token has expired, re-authenticate directly with openshell gateway login "$OPENSHELL_SAW_NAME". Running make openshell-saw-configure-gateway again also works, because it registers the gateway anew and signs you in. make whoami shows when the make login token expires, and make login renews it.

Change the defaults before exposing the cluster

The openshell-keycloak chart ships with test defaults that are not safe for production.

Test users with passwords equal to their names

The testUsers list in charts/openshell-keycloak/values.yaml creates four users: developer/developer, admin/admin, alice/alice, and bob/bob. To change these passwords, override keycloak.testUsers in charts/openshell-keycloak/values.yaml or remove the test users entirely and create accounts through the Keycloak admin console.

Self-registration enabled

registrationAllowed: true lets anyone with access to the Keycloak login page create their own account. Set keycloak.registrationAllowed to false in charts/openshell-keycloak/values.yaml before you expose the cluster.

PostgreSQL password

The database password for Keycloak’s PostgreSQL instance defaults to keycloak-db-pass (postgres.password in charts/openshell-keycloak/values.yaml). Override postgres.password before deploying.
