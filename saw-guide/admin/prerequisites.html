Prerequisites and sizing

SAW provisions one VirtualMachine per user, so your cluster needs to support OpenShift Virtualization and have enough capacity for every VM you plan to run. This page walks through each prerequisite, gives you a command to verify it, and ends with a sizing formula you can plug your own numbers into.

The SAW repository includes a make check-prereqs target that checks operators and CLI tools in one pass. You can run it after logging into the cluster to get a quick summary, but we cover each prerequisite individually below so you understand what it checks and why.

Cluster requirements

OpenShift 4.22 or later

SAW targets OpenShift 4.22 as its minimum version.

Check: Run oc version and confirm the server version is 4.22 or later.

oc version
Bare metal or supported cloud platform

OpenShift Virtualization runs VMs through KVM, which requires either bare-metal nodes or a cloud platform that exposes hardware virtualization. Check the compatible platforms list before planning your deployment.

Check: Before you install OpenShift Virtualization, verify that a worker node exposes hardware virtualization. A count above 0 means the CPU offers Intel VT-x or AMD-V.

oc debug node/<node-name> -- chroot /host grep -c -E 'vmx|svm' /proc/cpuinfo

After you install OpenShift Virtualization, confirm that it marked at least one node as schedulable for VMs, as shown in Verify the operators.

Default StorageClass with ReadWriteOnce support

The golden VM image creates a DataVolume with ReadWriteOnce access mode, and each user VM clones a disk from that DataVolume. Your cluster needs a default StorageClass that supports ReadWriteOnce PVCs.

Check: Confirm a default StorageClass exists and note its provisioner.

oc get storageclass

Operators

The manual install path needs two operators, OpenShift Virtualization and Red Hat build of Keycloak. The GitOps path also needs the External Secrets Operator. Only the pattern-secrets chart uses it, and only the GitOps path deploys that chart. make check-prereqs checks for the first two operators only. On the GitOps path, values-prod.yaml subscribes to all three operators for you. On the manual path, you subscribe to them yourself, as shown in Install the operators on the manual path. Either way, they must be installed before the first sandbox can run.

The GitOps path also subscribes to Red Hat Developer Hub (rhdh, channel fast) and OpenShift AI (rhods-operator, channel fast) through values-prod.yaml. If you do not plan to use them, you can remove those subscriptions from your fork.

Install the operators on the manual path

Skip this section on the GitOps path. Each step below applies a manifest with oc apply -f - and needs cluster-admin access.

  1. Subscribe to OpenShift Virtualization.

    The manifest creates the openshift-cnv Namespace, an OperatorGroup that targets it, and a Subscription to the kubevirt-hyperconverged package on the stable channel.

    oc apply -f - <<'EOF'
apiVersion: v1
kind: Namespace
metadata:
  name: openshift-cnv
  labels:
    openshift.io/cluster-monitoring: "true"
---
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: kubevirt-hyperconverged-group
  namespace: openshift-cnv
spec:
  targetNamespaces:
    - openshift-cnv
---
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: kubevirt-hyperconverged
  namespace: openshift-cnv
spec:
  channel: stable
  name: kubevirt-hyperconverged
  source: redhat-operators
  sourceNamespace: openshift-marketplace
EOF

    Check: Wait until the ClusterServiceVersion in openshift-cnv reports Succeeded.

    oc get csv -n openshift-cnv

  2. Create the HyperConverged resource.

    The subscription installs only the OpenShift Virtualization operator. The operator deploys OpenShift Virtualization itself once a HyperConverged resource exists. Without that resource, no node gets the kubevirt.io/schedulable=true label, and no VM can be scheduled. The GitOps path creates the same resource through the openshift-cnv chart.

    oc apply -f - <<'EOF'
apiVersion: hco.kubevirt.io/v1beta1
kind: HyperConverged
metadata:
  name: kubevirt-hyperconverged
  namespace: openshift-cnv
spec: {}
EOF

    Check: Confirm that at least one node is schedulable for VMs.

    oc get nodes -l kubevirt.io/schedulable=true

  3. Subscribe to Red Hat build of Keycloak.

    If your cluster already runs RHBK in another namespace, skip this step and follow If your cluster already runs RHBK instead.

    The operator goes into the Keycloak namespace, which is saw-keycloak unless you set KEYCLOAK_NS. The manifest is the one that make check-prereqs prints when the operator is missing: an OperatorGroup that targets the namespace and a Subscription to rhbk-operator on the stable-v26 channel.

    oc create namespace "${KEYCLOAK_NS:-saw-keycloak}" --dry-run=client -o yaml | oc apply -f -
oc apply -f - <<EOF
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: ${KEYCLOAK_NS:-saw-keycloak}-og
  namespace: ${KEYCLOAK_NS:-saw-keycloak}
spec:
  targetNamespaces:
    - ${KEYCLOAK_NS:-saw-keycloak}
---
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: rhbk-operator
  namespace: ${KEYCLOAK_NS:-saw-keycloak}
spec:
  channel: stable-v26
  name: rhbk-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
EOF

If your cluster already runs RHBK

Some clusters already run Red Hat build of Keycloak in another namespace, for example as the identity provider for the cluster login. The reuse steps in this section apply to the manual path, where make keycloak deploys Keycloak. The GitOps path always subscribes its own RHBK operator in saw-keycloak, so on that path follow the caution at the end of this section.

Check whether your cluster runs the RHBK operator:

oc get csv -A | grep rhbk

If the output shows RHBK in a namespace other than saw-keycloak, reuse that operator instead of installing a second one. Set KEYCLOAK_NS to that namespace in the shell where you run every later step, because the make targets fall back to saw-keycloak when it is unset. Then check whether a Keycloak instance already runs in that namespace:

export KEYCLOAK_NS=<namespace>
oc get keycloak -n "$KEYCLOAK_NS"

What make keycloak does during the manual install depends on that output:

  • If it lists another Keycloak but not SAW’s own openshell-keycloak, and that Keycloak already passes the check that make keycloak-check runs, the target uses it and deploys nothing.

  • If it lists another Keycloak but not openshell-keycloak, and that Keycloak is not yet configured for OpenShell, run make keycloak USE_EXISTING_KEYCLOAK=yes. The target then imports only the openshell realm into that Keycloak. It deploys no second Keycloak and no database, and it leaves the other realms alone. Without USE_EXISTING_KEYCLOAK, the target asks before it imports the realm, and it stops with an error when it runs without a terminal. If that Keycloak already has an openshell realm that fails the check, the target imports nothing and stops with Error: realm 'openshell' already exists on '<keycloak>' but is not configured for OpenShell. Fix what the check reports in that realm, then run the target again.

  • If it lists openshell-keycloak, alone or next to another Keycloak, or lists no Keycloak, the target deploys or updates SAW’s Keycloak and its PostgreSQL database in that namespace, managed by the existing operator. USE_EXISTING_KEYCLOAK makes no difference in this case.

Do not subscribe a second RHBK operator, for example in saw-keycloak, unless it uses the same channel and installs the same version as the existing one. The operator’s CRDs are cluster-scoped, so both installations share them. OpenShift provides only limited support for different versions of one operator on a cluster, and it supports them only when they ship the exact same CRDs. In other cases, the integrity of the Keycloak resources that the existing instance depends on cannot be guaranteed. A matching channel alone doesn’t guarantee the same CSV and CRDs. For example, a subscription with manual install plan approval stays on an older version of its channel until an admin approves the update. Look up the channel of the existing subscription and the version of the installed operator:

oc get subscriptions.operators.coreos.com -A | grep rhbk
oc get csv -A | grep rhbk

On the manual path, reuse the existing operator as described above. If you need a second operator anyway, run export KEYCLOAK_NS=saw-keycloak first, then apply the RHBK manifest with that channel in place of stable-v26. Otherwise the manifest reads the KEYCLOAK_NS that you exported above and applies a second OperatorGroup and the rhbk-operator Subscription in the namespace of the existing operator. When the new operator is installed, run oc get csv -A | grep rhbk again and confirm that both namespaces list the same version. Keep KEYCLOAK_NS=saw-keycloak for every later step.

On the GitOps path, values-prod.yaml subscribes rhbk-operator in saw-keycloak on stable-v26, whether or not RHBK already runs elsewhere. Before you install, set channel under clusterGroup.subscriptions.rhbk in your fork’s values-prod.yaml to the channel of the existing subscription. After the install, compare the installed versions with the same oc get csv command.

Verify the operators

Check: Confirm the operators are installed and their ClusterServiceVersions report Succeeded.

oc get csv -n openshift-cnv
oc get csv -n "${KEYCLOAK_NS:-saw-keycloak}"

Check: Confirm that OpenShift Virtualization marked at least one node as schedulable for VMs. On the manual path, this happens only after you create the HyperConverged resource.

oc get nodes -l kubevirt.io/schedulable=true

On the GitOps path, also check the External Secrets Operator, which the manual path does not need.

oc get csv -A | grep external-secrets

CLI tools

You need these tools on the workstation where you run make targets or openshell-saw commands.

Tool Version Purpose

oc

Matching cluster version

helm

3.x

Deploys SAW Helm charts

openssl

Any recent version

Generates PKCE challenges for the OIDC login flow

curl

Any recent version

Calls the Keycloak OIDC endpoints in make login

jq

Any recent version

Reads JSON in make login, in make openshell-saw-create, and in the OIDC check of the manual install

python3

Any recent version

Receives the browser callback of make login and decodes the saved token in make openshell-saw-create

virtctl

Matching cluster version

SSH access to VMs and VM lifecycle commands

openshell

0.1.2-rhaiv.0

OpenShell CLI for gateway and sandbox management

podman

Newer than 4.3.0 recommended (1.5 and 1.6 are rejected)

Required by pattern.sh in the GitOps install path

make login stops with an error when curl, jq, or openssl is missing, and its default browser flow also runs python3. make openshell-saw-create doesn’t check for its tools. Unless you set OWNER, it reads your identity from the token that make login saved, with jq and python3. Without python3, you can still sign in with the device code flow of make login OIDC_FLOW=device. make openshell-saw-create then can’t read the token, though, and it stops with Error: Not authenticated. Run 'make login' to sign in before creating a sandbox. even though you are signed in.

Install the openshell CLI as described in Install the OpenShell CLI. OpenShell also ships an install.sh script, but on macOS with Apple Silicon it installs a Homebrew formula and starts a local gateway as a Homebrew service, which SAW doesn’t need. For SAW, the release archive for your platform is the simpler choice.

An older openshell binary earlier in your PATH shadows the one you just installed. List every openshell your shell finds and check the version of the one it runs:

type -a openshell
openshell --version

Your shell runs the first path that type -a prints. If that is an older binary, remove it or put the new binary first in your PATH.

Check: Verify each tool is available.

oc version --client
helm version --short
openssl version
curl --version
jq --version
python3 --version
virtctl version --client
openshell --version
podman --version
virtctl and openshell are warnings, not hard errors, in make check-prereqs. You can install operators and Keycloak without them, but you need virtctl to SSH into VMs and openshell to manage gateways and sandboxes.

Sizing

Each user VM consumes a fixed block of CPU, memory, and storage. On top of that, the shared services (operators, Keycloak, Vault, golden image) add a baseline overhead that does not grow with the number of users.

Resource Per sandbox VM Cluster overhead

CPU

4 cores

8 cores

Memory

8 GiB

16 GiB

Storage

40 GiB (VM disk)

50 GiB (golden image, registry)

Worked example: 10 users

To estimate capacity for 10 concurrent users, add the overhead once and the per-VM numbers ten times:

  • CPU: 8 + (10 x 4) = 48 cores

  • Memory: 16 + (10 x 8) = 96 GiB

  • Storage: 50 + (10 x 40) = 450 GiB

These are minimums. Production clusters should add headroom for node failures, Pod scheduling, and any workloads running alongside SAW.

GPU passthrough

Experimental: in review

GPU passthrough is not part of the baseline. It is proposed in PR #37 (status as of 2026-10-02) and may change or be dropped before it merges. See Experimental and upcoming features for what it will change.
