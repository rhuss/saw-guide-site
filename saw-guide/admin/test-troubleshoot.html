Test and troubleshoot

This page helps you confirm that SAW works after installation and find the root cause when something goes wrong.

Offline tests

The SAW repository includes a Python test suite that validates the in-guest installer, the Helm charts, the CLI, and supporting scripts. These tests run without a cluster.

make test-installer

Check: the test runner prints a summary with zero failures.

The suite covers BOM validation, component installation, signing modes, profile parsing, credential resolution, pruning, reconcile logic, and chart rendering. CI runs the same suite on every push and pull request (Python 3.12 and 3.14, with helm lint and a bundle drift check).

A separate workflow signs the installer bundle with cosign. If you change apply_bom.py or the shipped provider profiles without re-signing, the bundle drift check catches the mismatch in CI.

Shell E2E tests

The headless E2E test (make test) wraps scripts/e2e-test.sh, which auto-detects the first configured provider and runs the full quickstart flow without interactive prompts. Four additional shell scripts test specific aspects of the stack on a live cluster. All of them require oc logged in, OpenShift Virtualization and RHBK operators installed, a built gateway image, and provider API keys in ~/values-secret.yaml.

tests/test-bootc-e2e.sh

Exercises the complete pipeline: Keycloak deployment, bootc image build, golden image import, provider Secret creation, VM boot from the golden image, cloud-init completion, OpenShell package installation, and Route creation with correct TLS termination.

tests/test-access-control.sh

Proves per-user access control through oauth2-proxy. Two users (alice and bob) in a shared namespace each get their own sandbox, and the test verifies that neither can reach the other’s gateway or dashboard (HTTP 403).

tests/test-multiuser-isolation.sh

Validates cross-namespace isolation. Alice creates a sandbox in saw-alice, then bob logs in and confirms he cannot see Alice’s sandboxes or access her gateway. Bob creates his own sandbox in saw-bob and verifies access to it.

tests/test-oidc-templates.sh

An offline validation that the Keycloak, pattern-secrets, and sandbox chart templates render correctly. Requires only helm on the path.

The shell E2E scripts need a running OpenShift cluster with the operators deployed. They are not part of make test-installer and were not executed during the writing of this guide.

Smoke test after install

After you complete either the GitOps install or the manual install, walk through these steps to confirm the deployment is healthy.

  1. Check the pattern status.

    make status

    Check: every SAW namespace appears, Helm releases show deployed, and VirtualMachine objects show Running.

  2. Verify the VM is running and the in-guest installer finished.

    make openshell-saw-status OPENSHELL_SAW_NAME=alice

    Check: the output is valid JSON from /var/lib/saw/status.json with "phase": "Done" for both the install and apply sections. If the apply section shows Running, the installer is still configuring workspaces and providers inside the VM. Wait a few minutes and check again.

  3. Confirm the gateway Route is reachable.

    oc get route alice-gateway -n saw-alice

    Check: the Route has a hostname and shows Admitted. The gateway Route uses passthrough TLS, so the VM terminates TLS itself.

  4. Register the gateway, log in as a test user, and list sandboxes. make openshell-saw-configure-gateway extracts the gateway CA, registers the gateway as alice, and makes it your active gateway. Registering the gateway opens the Keycloak login in your browser, where you log in as alice.

    make openshell-saw-configure-gateway OPENSHELL_SAW_NAME=alice
openshell sandbox list --gateway alice

    Check: the command returns a list of sandboxes (or an empty list if no sandboxes are configured in the BOM profile). If you receive a token error, run openshell gateway login alice first.

  5. Open the OpenClaw UI of the notebook sandbox through a port forward. The target below needs the gateway CA and alice as your active gateway, which the previous step set up.

    make openclaw-gui OPENSHELL_SAW_NAME=alice SANDBOX_NAME=notebook

    The target reads the OpenClaw token from the sandbox with openshell sandbox exec and prints http://localhost:18789/#token=<token>. It then forwards port 18789 from the sandbox to your machine until you press Ctrl-C. Open the printed URL in your browser.

    Before it forwards the port, the target stops every process on your machine that has the local port (18789 by default) open. To use a different local port, add GUI_PORT=<port> to the command.

    Check: the OpenClaw web UI loads without a Keycloak login, because the token in the URL authenticates the session.

    SAW sets up the Route named dashboard for the OpenClaw agent UI, not for the OpenShell Dashboard. At this baseline OpenClaw listens inside the sandbox container, which has no network of its own, so the Route does not reach the OpenClaw UI. Use the port forward above instead. The OpenShell Dashboard is behind the Route named webui. See Architecture for the full Route mapping.

Debugging tools

When a smoke-test step fails, these Makefile targets help you find the root cause.

make status

Prints all SAW namespaces, Helm releases, VirtualMachine and VMI objects, prepare Jobs, ImageStreams, and Builds. Run this first to get an overview of every resource in the cluster.

make openshell-saw-logs OPENSHELL_SAW_NAME=<name>

Follows the VM serial console log. This is where the in-guest installer writes its progress, including every [saw-installer] line. Watch it while a VM is booting to see the install and apply steps in real time.

make openshell-saw-status OPENSHELL_SAW_NAME=<name>

Reads /var/lib/saw/status.json from inside the VM over SSH. The status file has one section per installer step (install and apply), each with a phase (Running, Done, or Failed), a bom name, a message for failures, and an updatedAt timestamp. The ready marker file at /var/lib/saw/ready exists only when both steps succeeded for the same BOM.

make openshell-saw-vm-ssh OPENSHELL_SAW_NAME=<name>

Opens an interactive SSH session on the gateway VM as cloud-user. The target adds your SSH public key to the <name>-ssh-pubkey Secret if the Secret doesn’t hold it yet, waits until the VM accepts the key through the KubeVirt guest agent, then runs virtctl ssh.

You can run a single command without an interactive session:

make openshell-saw-vm-ssh OPENSHELL_SAW_NAME=alice CMD='sudo journalctl -u saw-install --no-pager -n 50'

Make expands $(…​) in CMD=, so write $$(…​) or call scripts/openshell-saw-vm-ssh.sh directly if you need command substitution inside the VM.

make openshell-saw-list

Lists every SAW sandbox across all namespaces, showing the Helm release status and the VM’s printableStatus.

Troubleshooting

Symptom Likely cause Fix

VM stays in Provisioning or WaitingForVolumeBinding for more than ten minutes.

The golden image DataVolume has not finished importing, or the storage class does not support ReadWriteOnce access.

Check oc get dv -n <namespace> for import progress. Confirm your default StorageClass supports ReadWriteOnce. See Prerequisites for storage requirements.

make openshell-saw-create prints Press Enter to set owner to '<user>', or type a different owner: and doesn’t continue.

Unless OWNER is set, the target reads your user name from the token that make login saved and waits for you to confirm who owns the VM.

Press Enter to make yourself the owner. In a script, pipe in an empty line by putting printf '\n' | in front of the make command, so that the target still detects your subject. Setting OWNER=<name> skips both the prompt and the subject detection, so the installer adds no workspace member unless you also set OWNER_SUBJECT. See step 11 of Install manually.

After make openshell-saw-create, the gateway accepts no Keycloak login, and helm get values "$OPENSHELL_SAW_NAME" -n "saw-$OPENSHELL_SAW_NAME" -o json | jq -r .oidc.issuerUrl prints null.

KEYCLOAK_NS did not name the namespace of your Keycloak when you ran the target, for example in a new terminal where you set only OPENSHELL_SAW_NAME. The target then finds no OIDC issuer and deploys the gateway without OIDC. It reports no error.

Export the namespace of your Keycloak as KEYCLOAK_NS and run make openshell-saw-create again with the same variables. Then restart the VM with make openshell-saw-restart, because the issuer is part of the installer ConfigMap. If you registered the gateway in that terminal as well, run make openshell-saw-configure-gateway again so that your CLI signs in through Keycloak.

The apply stage stops with credential for provider 'brave' in workspace 'default' not found, in the VM console log and in the message that make openshell-saw-status shows.

Both bundled SAW-BOM profiles create a brave provider whose credential comes from the Secret web-search. make openshell-saw-create creates that Secret only when the environment variable WEB_SEARCH_API_KEY holds a key. WEB_SEARCH is a different variable and does not create it.

Export KEYCLOAK_NS and OPENSHELL_SAW_NAME as in step 3 of Install manually, because a run that finds no Keycloak in KEYCLOAK_NS deploys the gateway without OIDC. Then run make openshell-saw-create again with WEB_SEARCH_API_KEY set in front of make and the same other variables, as in step 11 of Install manually. Afterwards, restart the VM with make openshell-saw-restart, because the VM attaches the provider Secrets as disks when it starts. No sandbox in the bundled profiles attaches the brave provider, so the key gives the agents no web search (see BOM and profiles).

The VM console log shows verify-bundle is not in this golden image; staging without verification, and make openshell-saw-status lists the OpenShell components as unsigned.

At this baseline, quay has no golden image under the tag in OPENSHELL_VERSION, so make copy-images mirrored latest. That image predates the installer bundle verifier verify-bundle. The unsigned entries have a separate cause: the baseline BOM gives no component a signature, so they appear in warn mode with any golden image.

In the default warn signing mode the VM installs anyway, while in enforce mode the install stops. To get the verifier, build the golden image from the baseline with make build-gateway-podman instead of mirroring it (see Build the golden image from your checkout). Existing VMs keep their root disks, so only VMs created after the build get the verifier. The components stay unsigned until the BOM gives them a signature (see Signing modes).

The in-guest installer fails with a signature verification error (image …​ is not signed by …​).

The BOM entry has a signature block, but the image is not signed by the expected key, or the public key file is missing from /etc/saw/trust in the golden image.

Check the signing mode in Day 2 operations. If you are testing without signed images, set signing.mode to off or warn in the chart values. In enforce mode, every component image must pass a cosign verification against a key under /etc/saw/trust.

CreateProvider is denied with provider profile '<type>' not found or unsupported provider type.

The provider type in the BOM profile is not a governance profile ID known to the gateway. Governed profiles come from the governance interceptor, which must be running and connected.

Confirm the governance interceptor Pod is healthy in the openshell-agents namespace. Check that the provider type in your BOM profile matches a profile ID from the governance policy ConfigMap. See Governance for how profile IDs are defined.

Every mutation (sandbox create, provider update, config change) fails with PERMISSION_DENIED.

The governance interceptor’s failure_policy is set to fail_closed (the chart default at governance.failurePolicy), but the interceptor is unreachable or crashed. When fail-closed is active, the gateway rejects all intercepted operations if the interceptor does not respond.

Check the interceptor Pod logs in openshell-agents. Restart the interceptor Deployment if it is in CrashLoopBackOff. See Governance for the fail-closed behavior.

Policy updates are denied after an interceptor restart, with a message about stale governance annotations.

The interceptor generates a fresh Ed25519 signing key on every process start. Sandboxes created before the restart carry the old key’s ID. UpdateConfig validation rejects them because the key ID no longer matches.

Recreate the affected sandboxes so they pick up the new key. CreateSandbox is not affected because it always injects the current key. This is by design, not a bug.

OIDC token expired (token is expired or 401 Unauthorized).

An access token is valid for at most 10 hours after you sign in. The openshell-cli client asks for 24-hour tokens, but Keycloak never issues an access token that outlives the login session, and the realm keeps Keycloak’s default SSO Session Max of 10 hours. The refresh token expires after 30 minutes without use, and the CLI tries it only when the access token is about to expire, so with these defaults the refresh fails.

Run openshell gateway login <name> to obtain a fresh token. If you are scripting, use the Keycloak ROPC grant to get a new token. See Token lifetime for the Keycloak settings, and Token lifetime and re-authentication for what users see when their token expires.

openshell sandbox list shows a sandbox in the phase Error. openshell sandbox get <sandbox-name> shows the condition Ready as False, with a message that starts with Container terminated by signal. In the VM, podman ps -a lists the sandbox’s supervisor container, openshell-supervisor-<sandbox-id>, as exited.

The OpenShell supervisor container that runs next to the sandbox has exited. The gateway’s Podman driver counts a sandbox as ready only while its supervisor runs, and it stops the sandbox container when the supervisor is gone.

The gateway restarts a sandbox in this condition only when the gateway itself starts, for example when the VM boots, and only if the sandbox container still exists. A VM restart with make openshell-saw-restart interrupts all of the user’s sandboxes, so the steps below recreate only this sandbox from the BOM instead.

Deleting a sandbox also deletes its /sandbox volume, openshell-sandbox-<sandbox-id>-workspace, with all files in it. Running only sudo systemctl restart saw-apply doesn’t keep the files either, because the apply step itself deletes and recreates a sandbox whose openshell sandbox get output contains Error.

Open a shell on the VM with make openshell-saw-vm-ssh OPENSHELL_SAW_NAME=<name>. The volume keeps the sandbox’s files until you delete the sandbox, so copy out the files you want to keep first. The <sandbox-id> in the name of the supervisor container is the sandbox ID, and podman volume export openshell-sandbox-<sandbox-id>-workspace --output <file>.tar writes the content of the volume to a tar file. Then delete the sandbox and run the apply step again:

openshell sandbox delete <sandbox-name>
sudo systemctl restart saw-apply

In the VM, the openshell CLI talks to the local gateway with the installer’s admin identity. For a sandbox outside the default workspace, add --workspace <workspace> to the delete command. systemctl restart returns when the apply step has finished, and make openshell-saw-logs on your machine shows its progress.

The apply step creates every enabled sandbox of the BOM profiles that is missing. In each OpenClaw and NemoClaw sandbox that has a provider, it enables the keep-alive unit openshell-sandbox-<sandbox-name>, which keeps the sandbox ready. When the installer knows the provider’s endpoint, from a base URL in the provider’s Secret or for the provider types nvidia, build, and openai, it also configures OpenClaw with a new token. Read the new token before you open the OpenClaw UI again (see Open the OpenClaw web UI).

Sandbox or workspace creation fails with a name validation error.

The name is longer than 19 characters, contains uppercase letters, or is not a valid DNS label. The installer enforces a 19-character limit because OpenShell workspace and sandbox names become part of Kubernetes resource names that must fit DNS constraints.

Choose a shorter, lowercase name that matches the regex ^[a-z0-9]([a-z0-9-]*[a-z0-9])?$. See the naming rules in the onboarding page.

The dashboard Route opens neither the OpenClaw UI nor the OpenShell Dashboard.

SAW sets up the Route named dashboard for the OpenClaw agent UI and forwards it to port 18789 of the VM. At this baseline OpenClaw listens inside the sandbox container, which has no network of its own, so the Route does not reach the OpenClaw UI. The OpenShell Dashboard is behind the Route named webui.

Open the OpenClaw UI through a port forward, with make openclaw-gui as in the smoke test or as described in Open the OpenClaw web UI. To reach the OpenShell Dashboard, open the webui Route. See Architecture for the Route naming table.
