How governance works

The architecture overview shows that every user VM runs its own OpenShell gateway. That raises a practical question: how does the platform enforce a single, consistent policy across all of those gateways? The answer is the governance interceptor, a standalone gRPC service that sits between every gateway and its sandbox operations.

Figure 1. How governance flows from Git through the interceptor to every gateway. Running sandboxes keep their policy because the reload push targets 127.0.0.1 inside the interceptor Pod.

One interceptor, many gateways

SAW deploys the governance interceptor as a single-replica Deployment in the openshell-agents namespace. It listens for gRPC on port 18081 and is the only process that holds the admin-signed sandbox policy and provider profiles. A NetworkPolicy restricts ingress to virt-launcher Pods from namespaces labeled openshell.pattern/saw=true, so only the gateway VMs can reach it.

One replica is enough because the interceptor protocol is stateless per call. Each evaluation request carries the gRPC method name (for example CreateSandbox), the caller’s principal, and the proposed operation. There is no session, no gateway-specific state, and no affinity requirement. Every gateway in the cluster connects to the same endpoint and receives the same policy enforcement.

What a gateway asks, and when

At startup, each gateway calls Describe on the interceptor to learn which operations it governs. The same call checks that both sides come from compatible OpenShell releases (see Interceptor and gateway versions). The gateway builds an immutable execution plan from that response. Changing the interceptor’s bindings requires a gateway restart because registration is static.

For each intercepted API call, the gateway evaluates the request in phase order: modify_operation first, then validate, and finally post_commit after the handler commits. If the interceptor is unreachable or returns an error, the gateway’s fail_closed failure policy rejects the operation before handler dispatch. A valid deny result (the interceptor returning allowed=false) always rejects, regardless of the failure policy.

The gateway TOML that SAW renders into each VM shows the full configuration. It opens with [openshell] version = 2, the configuration schema that gateways of the 0.1 release series require. They refuse to start with a file that lacks it.

# Source: https://github.com/validatedpatterns-sandbox/secure-agent-workspace/blob/4768f02d4415449de74403df62bad0c03630448e/charts/openshell-saw/templates/_helpers.tpl (rendered with defaults)

[openshell]
version = 2

[openshell.gateway]
compute_driver = "podman"
provider_profile_sources = [
  { type = "interceptor", name = "governance" },  (1)
]

[[openshell.gateway.interceptors]]
name           = "governance"
grpc_endpoint  = "http://governance-interceptor.openshell-agents.svc.cluster.local:18081"  (2)
allow_insecure_transport = true   (3)
order          = 10
failure_policy = "fail_closed"    (4)
binding_policy = "allowlist"      (5)
timeout        = "500ms"

[[openshell.gateway.interceptors.bindings]]  (6)
rpc = "openshell.v1.OpenShell/CreateSandbox"
phases = ["modify_operation", "validate"]

[[openshell.gateway.interceptors.bindings]]
rpc = "openshell.v1.OpenShell/CreateProvider"
phases = ["validate"]

[[openshell.gateway.interceptors.bindings]]
rpc = "openshell.v1.OpenShell/UpdateConfig"
phases = ["validate"]

[[openshell.gateway.interceptors.bindings]]
rpc = "openshell.v1.OpenShell/SubmitPolicyAnalysis"
phases = ["validate"]
1 The gateway fetches provider profiles exclusively from the interceptor. The provider_profile_sources list contains only the interceptor source, so profiles users import are not used.
2 The endpoint resolves to the in-cluster Service DNS name of the interceptor Deployment in openshell-agents, on port 18081.
3 Traffic between gateway and interceptor stays inside the cluster as plaintext gRPC (allow_insecure_transport = true). No JWT authentication is performed on these calls.
4 fail_closed means any interceptor failure (timeout, crash, network partition) blocks the operation rather than letting it through.
5 binding_policy = "allowlist" means only the bindings listed below take effect. If the interceptor’s manifest advertises additional bindings, they are ignored.
6 Four operations are bound. CreateSandbox runs in both modify_operation (policy injection) and validate (signature check) phases. CreateProvider, UpdateConfig, and SubmitPolicyAnalysis run in validate only.

Provider profiles follow the ConfigMap

The governance interceptor reads provider profiles from a directory mounted as a ConfigMap volume. Seven profiles ship with SAW: brave, gemini, github, nvidia, openai, slack, and web-search. The admin controls which profiles are available by editing the governance-policy chart and pushing to Git. Argo CD syncs the change, kubelet propagates the updated ConfigMap into the Pod (typically within about 60 seconds), and the interceptor picks up the new files on the next evaluation.

A profile names the endpoints a provider may reach and, in its binaries list, the executables allowed to use those endpoints. Every profile has to list them, because a missing or empty binaries list allows nothing: the profile then lets no process reach its endpoints. The openai profile, for example, lists curl and the node binary that OpenClaw runs under, at the paths the sandbox images use. When you add your own profile, check these paths against the image your agents run in.

Because provider_profile_sources points only at the interceptor, the gateway’s profile catalog is whatever the interceptor serves. OpenShell has no built-in profile catalog at this release, and the gateway rejects a { type = "builtin" } source. The only other source type, user, holds imported profiles, and SAW leaves it out. The gateway calls SnapshotProviderProfiles on each provider lookup, so profiles are never cached by the gateway. When a user runs CreateProvider, the interceptor’s validate phase checks that the provider type matches a managed profile ID and denies the request if it does not.

The interceptor signs every profile it serves. The upstream example stores the signature, the profile hash, and the signing key ID as three annotations, but SAW’s interceptor image keeps only the signature. That patch works around NVIDIA/OpenShell#3929. SAW’s image build describes the bug this way: a profile with more than one annotation gets a different revision on every gateway call, so a sandbox that uses the provider never finishes starting. Nothing is lost, because the signature is a JWT that already carries the hash as a claim and the key ID in its header.

Sandbox policy is fixed at creation

When a user creates a sandbox, the interceptor’s modify_operation phase injects the current admin policy into the creation request and stamps a cryptographic signature. The subsequent validate phase verifies that the policy matches the signed baseline. From that point forward, the sandbox carries a specific, signed policy revision.

When the admin updates policy.yaml in Git, the interceptor’s file watcher detects the change, re-reads the file, and re-signs it with the current key. It then attempts a reload push: it calls ListSandboxes and UpdateConfig on the gateway endpoint configured as --gateway-endpoint.

SAW sets gatewayEndpoint to https://127.0.0.1:17670, which is the gateway address inside the interceptor Pod itself. Since the interceptor does not run inside a user VM, this reload push never reaches any user gateway. Running sandboxes keep their policy until they are destroyed and recreated. Only new sandboxes pick up the updated policy through CreateSandbox.

We can trace this in the diagram: the reload push arrow loops back to 127.0.0.1 and stops at the interceptor Pod boundary. New sandboxes always receive the current signed policy.

Who wins in a policy conflict

If a user attempts to change a sandbox’s policy through the CLI (openshell policy set) or the SDK, that call reaches the gateway as an UpdateConfig request. The interceptor’s validate phase checks for a valid governance signature on the policy payload. An unsigned or stale-signed change is denied with PERMISSION_DENIED, and nothing is merged. The user sees the interceptor’s denial reason and no policy revision is created.

Admins change policy through Git, not through the CLI. The admin edits policy.yaml, pushes to the repository, and Argo CD syncs the updated ConfigMap into the interceptor Pod. The interceptor re-signs the new policy, and from that moment every new sandbox receives it.

After an interceptor restart, the signing key changes because the interceptor generates a fresh Ed25519 key per process start. Sandboxes created before the restart carry the old key’s ID in their policy signature. An UpdateConfig call on those pre-restart sandboxes is denied because the key ID no longer matches. CreateSandbox is unaffected because the modify_operation phase always injects a fresh signature with the new key.

OpenShell also supports a global policy at the gateway level that replaces all sandbox policies. RFC 0002 (Agent-Driven Policy Management) defines an "org ceiling" concept that caps the maximum capability envelope for agent-proposed policy changes. Both mechanisms are upstream features, separate from the interceptor-based governance that SAW deploys.

Turning governance off

If the governance.enabled flag is set to false in the openshell-saw chart values, the gateway TOML omits the interceptor block and the provider_profile_sources line. The gateway then uses its default source, which holds only imported profiles. When the BOM names a provider whose profile is missing, the installer imports the copy bundled with the openshell-saw chart, which exists for brave, nvidia, and openai. The installer skips every other provider with a warning until the admin either re-enables governance or imports its profile manually.

Sandboxes created without governance enforcement receive no admin-injected policy. The sandbox runs with whatever policy the user provides (or the image-bundled policy if none is specified, or the restrictive default if neither exists).

Interceptor and gateway versions

SAW requires the governance interceptor and the gateways to run the same OpenShell release. That rule is SAW’s own policy, and the protocol check that OpenShell runs is looser. When a gateway starts, it sends its version metadata in the Describe call, and the interceptor checks that metadata before it returns its manifest. If the gateway sends no metadata, speaks a different major version of the extension protocol, or lacks a capability the interceptor requires, the interceptor answers FAILED_PRECONDITION. Gateways from the 0.0.x series predate this exchange and send no metadata at all, so they always fail the check. The check works in the other direction too: the gateway rejects a manifest that carries no interceptor metadata.

Either way, the gateway doesn’t start, because a failed Describe call during startup is fatal. That’s stricter than the fail_closed policy, which only blocks the governed operations. A gateway that can’t negotiate with its interceptor serves no requests at all.

SAW keeps the two in step by building the interceptor from the same OpenShell tag the gateways come from. A GitHub workflow reads the tag from source.git.ref in image-builder-charts/helm/governance-interceptor-image/values.yaml. It builds the upstream interceptor example at that tag, applies the profile annotation patch described above, and tags the image with the same tag. The governance-interceptor chart then pulls ghcr.io/validatedpatterns-sandbox/governance-interceptor:v0.1.2, while each VM’s BOM installs the gateway build 0.1.2-rhaiv.0 of the same release.

Because all gateways share this one interceptor, and SAW pins it to the gateways' release, they move to a new OpenShell release series at the same time. On the move from the 0.0.x series the check itself enforces this: once the interceptor runs the new series, a 0.0.x gateway fails at its next start. Between later series, a gateway fails the check only if the protocol major version or the required capabilities change. We cover the steps in Day 2 operations.
